# 中间件管线

HTTP 请求处理管线按严格顺序执行，插件会根据优先级插入高、普通或低优先级阶段：

| 顺序 | 中间件 | 功能 |
|------|--------|------|
| 1 | BandwidthCounting | 追踪每个请求的入/出流量 |
| 2 | Cors | 路由级响应头和 OPTIONS 预检短路 |
| 3 | ResponseCompress | 响应压缩（gzip、brotli） |
| 4 | Plugin（高优先级） | 安全关键型插件；网页防篡改位于该阶段 |
| 5 | AccessControl | IP 黑白名单、地理封锁、连接数限制 |
| 6 | IpLog | 按 IP 记录请求日志 |
| 7 | AutoHttps | 强制 HTTP → HTTPS 重定向 |
| 8 | WafControl | 应用 WAF 规则（攻击模式匹配） |
| 9 | Captcha | 可疑流量触发验证码 |
| 10 | CcProtection | CC 攻击检测与封锁 |
| 11 | Throttled | 请求节流 |
| 12 | SpeedLimit | 限速执行 |
| 13 | CcResponseMonitor | CC 响应模式监控 |
| 14 | Plugin（普通/低优先级） | 分析、改写等插件中间件 |
| 15 | SimpleRes / FileProvider | Mock 响应或静态文件服务 |

中间件处理完成后，请求转发至 YARP 反向代理引擎进行路由和负载均衡。

每个中间件的执行方向、短路条件、配置来源和排障方法见博客专题：[深入 LyWaf 中间件：一次请求如何穿过完整防护链](blog/06-中间件管线详解.md)。

需要每个组件的独立文章时，查看 [LyWaf 中间件逐篇解析](blog/middleware/README.md)。

## 执行方向

请求按注册顺序向下执行，响应在 `await next(context)` 返回后逆序经过上游中间件。因此“注册在压缩前”不等于“响应阶段先于压缩”。修改响应头或响应体时必须同时考虑请求方向和回程方向。

## 短路与旁路

访问拒绝、验证码、限速和 Mock 响应可以不调用 `next`，这称为短路。观察型中间件内部失败时通常应记录后旁路，不能因为统计失败阻断业务。每个短路响应都应设置明确状态码、内容类型和必要的安全头。

## 排障方法

1. 确认请求命中了预期监听和路由。
2. 临时提高相关中间件日志级别。
3. 查找最先写入响应或未调用 `next` 的组件。
4. 对比禁用单项功能后的行为。
5. 检查上游是否实际收到请求。

不要随意调整管线顺序。移动组件前应验证 WAF、CORS 预检、压缩、静态文件、WebSocket 和插件优先级，至少执行一次端到端回归。
