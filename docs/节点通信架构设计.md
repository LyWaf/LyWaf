# LyWaf 节点通信架构设计

## 当前迭代：中控长连接拓扑

同一套 LyWaf 程序通过后台选择独立运行、作为中控或连接中控。角色与接入凭证保存在本机文件，角色变更明确提示重启；节点只填写中控地址和本节点凭证。新模式复用控制端口上的 WebSocket，所有 v2 业务客户端共用发送入口，断线不回退 HTTP 或节点直连。旧配置的 HTTP 通信仅作为兼容模式保留。

### 后台接入步骤

1. 在预定中控的独立“群集管理”菜单选择“群集中心（中控）”，保存并明确确认重启。中控仍可处理代理流量，不需要单独部署控制程序。页面地址为 `/#/cluster-management`，旧的 `/#/multi-node` 链接仍兼容。
2. 在中控的节点接入区域为每个节点分别创建接入凭证。凭证按密钥保护，不写入日志或公开配置示例，不在不同节点间复用。
3. 打开目标节点自己的后台，选择“连接中控”，填写中控控制端口的根地址和该节点的接入凭证，例如 `https://controller.example:7030/`，不是代理端口或 API 子路径。保存并确认重启。
4. 新接入默认启用“同步 CC 和运行状态”。检查页面的实际运行角色和同步状态，再在中控确认节点健康。保存不等于已应用，地址、角色及同步历史切换必须经确认重启。
5. 共享 CC 规则在各参与实例保持相同策略，选择集群或站点组作用域、使用中控成员和完整覆盖；手动成员留空。中控也属于成员，必须配置对应规则。配置分发是单独的明确任务，不因节点接入而自动覆盖业务配置。

节点只需能主动连接中控控制端口；托管消息通过既有 WebSocket 中转，不要求节点之间互通，也不要求中控主动访问节点管理端口。生产使用 HTTPS/WSS 和有效证书；凭证签名不能替代传输加密。中控不可用时节点继续代理，但不伪造完整的共享 CC 证据，权威挑战操作失败关闭。单中控文件权威是当前部署范围，不提供自动多中控接管。

节点接入的后台保存现在区分实际变更：相同角色、规范化后相同的中控地址及留空保留凭证，不写入新版本、不产生多余重启提示；重复保存待生效配置也不会偷偷激活新角色。切回当前运行配置可取消待重启状态。真正需要重启时显示按钮，复用现有服务重启 API，并使用中英文确认框说明排空和短暂断连；保存不自动重启，确认提交中及提交后阻止重复操作，失败不自动重试。

中控在握手中返回绑定集群、接收节点、请求 ID、控制进程 BootId、签名密钥和有效期的来源清单。清单包含历史节点标识，用于校验聚合数据来源；它不是在线列表，也不是全局 CC 覆盖率。节点断线会清除本地清单，过期清单不能继续授权转发来源。

自动 CC 成员配置的协议前置：握手新增 `ControlCapabilities.CcMembership=1`，仅在节点声明支持时，中控在签名证明中附加 `ExpectedCcNodes`。该清单包含中控及已启用的 Active/Draining 节点，不依据连接在线状态缩减，也不依据单个 RPC 的权限缩减；PendingApproval、Revoked 和禁用节点不纳入。排空但不能回答查询的成员应使覆盖不完整，不能静默删除来取得 Complete。清单与历史 `KnownNodes` 分离，受同一请求、集群、BootId、密钥和一分钟有效期约束，存储防止调用方修改，断线后失效。未协商时省略字段，保留旧证明规范签名。

托管中控现在自动生成并在本机持久保存 CC 解封签名私钥、挑战密钥和信任域。接入凭证只携带签名公钥及节点所需的挑战密钥，不分发中控签名私钥；已有明确配置的密钥迁移时保留。旧版不带这些字段的凭证仍可建立基础连接，但尚不能据此自动启用完整状态同步。

旧托管节点的授权材料升级已接入签名握手：双方通过 `ControlCapabilities.AuthorityBootstrap=1` 协商，中控将公钥、共享挑战密钥和信任域放入原有 HMAC 证明。只有已激活且获授验证码签发/消费操作的节点才获得这些材料；待批准、排空中或仅获授握手的节点仍只获得来源清单。未协商能力时不新增证明字段，保留旧客户端的规范签名格式。

节点校验集群、中控身份、请求、进程 BootId、时效、签名和材料格式后，只为缺少材料的旧凭证写入待生效配置。节点 ID、集群和传输密钥保持不变；已保存待生效的操作者修改不会被后台覆盖，已固定材料的变更不会静默接受。后台显示凭证升级待重启状态并自动刷新，保留未提交的地址和凭证草稿。确认重启后才应用新材料；这不自动开启运行状态同步。握手中包含共享挑战密钥，应按接入凭证等级保护，生产使用 HTTPS/WSS；HMAC 不提供保密性。撤销节点消息权限也不等于使其忘记已经获知的共享密钥，泄露时仍需明确轮换。

双方声明 `ControlCapabilities.SessionEnd=1` 后，节点正常停止会在既有长连接上发送带 `Ending=true` 的签名握手，中控将结束标记持久化。标记必须匹配该条 WebSocket 最初认证的 BootId 和当前登记会话；普通 HTTP、建立新连接时的 Ending、其他启动标识及已发生的身份冲突都不能借此关闭或恢复会话。正常结束后可立即接受新 BootId，旧启动标识进入已有退休历史且不能再次登记；仍需完成常规对账才开放配置任务。结束告知最多等待两秒，失败或异常断线时保留原有身份冲突保护，不伪造已确认结束。身份服务先于连接器启动、晚于连接器停止，确保告知时身份租约仍有效。

托管 CC 解封新增权威端的消费记录校验：请求节点、挑战摘要及代际绑定作用域必须对应，记录持久化且仅在短时间内有效，并继续核对中控规则与策略摘要。消费记录证明受信节点消费过该挑战，不是独立的人机答案证明；显式的旧版作用域授权保持兼容。

为避免开启运行状态同步后破坏节点私有验证码规则，`cc.captcha.release` 增加可选 `NodeRule` 定义。仅托管节点自己的 `node:<sender>` 命名空间可使用该定义，并要求 `Scope=Node`、规则 ID、启用状态、验证码动作、IP 主体和策略摘要一致，以及真实的、匹配节点/作用域/代际且未过期的消费记录；定义最多 64 KiB，不写入中控规则配置。即使存在显式授权，携带本地定义也不能跳过消费记录检查。站点组或集群范围不能借此提交自定义定义，仍必须匹配中控上的规则；未知共享规则不能仅凭消费记录解封。节点准入失败、记录存储故障或取消时不签发新的释放代际。

`ManagedCcReleaseTests` 验证私有命名空间、消费身份/主体/时效、策略摘要、撤销和排空状态、存储失败及取消等边界。`ManagedNodeCaptchaTests` 使用真实测试宿主与控制端口 WebSocket，验证中控不保存该本地规则时，节点仍能完成挑战签发/消费、中控签名、节点验证与持久应用，重复请求不递增代际，其他节点的同名规则不释放。同步关闭时仍沿用本地解封路径，不强行查询远端规则定义。此项是默认同步的前置兼容修复，尚未改变当前默认开关。

## 1. 目标与决策

支持不同机器、不同网络中的 LyWaf 实例进行配置分发、运行状态复制、健康采集和插件任务协调。节点断连不得阻塞正常代理请求。

推荐第一阶段采用单 Controller、多 Node、HTTPS + JSON、有界后台队列。复用现有 .NET HTTP 客户端和配置生命周期服务，不引入新的消息中间件，不立即实现多主控制、全局强一致或自定义 TCP 协议。

统一通信基础设施，不把所有业务强行统一成同一种一致性模型：

- 配置：单写者、版本化、灰度提交、结果确认和补偿回滚。
- 运行状态：本地优先、异步复制、最终一致。
- 指标和事件：异步上报或采集，标明时间与新鲜度。
- 不可重复任务：业务幂等及可选的强一致后端，不能依赖普通状态复制实现全局锁。

实现范围不包括任意远程命令、文件同步、程序自动升级和跨节点上传目录复制。HTTP 上传插件中的文件仍属于接收节点本地文件。

兼容版 Distribution 签名覆盖操作名、时间戳、nonce、正文摘要，不包含独立的发送者、接收者和集群标识。nonce已写入StateDirectory/replay，持久占用后才能执行。新增v2分发协议绑定发送者、接收者、集群、方法、路径与正文摘要，并使用独立的replay-v2目录；RuntimeState 已提供显式选择的 v2 批量传输，不自动降级到兼容协议。

v2 配置命令通过持久 Inbox 检查同消息 ID 的正文冲突；Outbox 在结果未知时只查询，不盲目重新执行。Controller 在发送前持久化 Unknown 和 pendingStage，重启核对结果不会自动推进批次。真实进程 prepare/commit/rollback 丢失 ACK 后恢复验证见 `node-communication-final-verification-2026-10-20.md`；这不等于所有文件系统断电窗口均已验证。

v2 通用协议错误统一包含 `success=false`、`errorCode`、`messageKey`、`traceId`；认证、运行状态授权、载荷及 Inbox 错误具有中英文资源。业务 ACK、验证码授权响应及发送端错误转译仍需分别验收，不能把此公共错误工厂视为整个协议已完成统一。

发送端错误读取已限制为 8192 字节（无长度头时最多读取 8193 字节以检测溢出）。仅保留受限格式的 `errorCode` 和 `traceId`，翻译键由本地生成，不采信远端错误全文或远端翻译键；HTTP 状态码和 Retry-After 保持原语义。签名新增独立 Node.js `node:crypto` 固定向量比对测试，见 `NodeSignatureVectorTests`。已知操作名由 `NodeProtocolOperations` 统一登记，启动配置中的未知操作、通配符和大小写错误会被拒绝，而不是静默保存无效权限。

现有 prepare/commit 是应用层分阶段发布，不是具有全局原子性保障的分布式数据库事务。部分节点可能暂时运行不同版本。

## 3. 拓扑与网络

```text
管理员 -> Controller 管理 API
             |
             +-- 配置命令 / 状态查询 --> Node A -> 本地代理与插件
             +-- 配置命令 / 状态查询 --> Node B -> 本地代理与插件
                                         ^
                      Node A <--- 状态复制 ---> Node B
```

第一阶段以同一私网或 VPN 可互通为部署前提。Controller 管配置，Node 不反向修改 Controller 配置。运行状态只在明确授权的复制组内传播，不能因为同处一个集群就自动共享所有状态。

建议先验证 3 节点环境，再以 20 节点作为第一阶段容量测试目标；这不是当前产品已经验证的容量上限。全互联 Peer 的连接和发送量随节点数增长，超过测试目标前必须重新压测，不能仅增加队列大小。

节点在 NAT 后、控制端不能主动连接时，第二阶段增加 Node 主动向 Controller 长轮询领取任务及回报结果。长轮询复用同一消息契约和幂等表，不另建一套业务流程。第一阶段不承诺 NAT 穿透。

生产只允许 HTTPS，校验证书链和主机名，禁止跳过 TLS 校验。agent 接口仅向可信节点开放，管理登录接口与 agent 权限分开；同端口兼容部署可保留，但不能因此让机器身份访问管理接口。公网部署优先 VPN 或独立受限通信监听，不能使用开放后台端口代替节点认证。

## 4. 节点身份与生命周期

持久身份为 `(ClusterId, NodeId)`；NodeId 初次部署生成并保存，禁止直接随机器名改变，也禁止克隆数据目录后让两个实例使用同一 NodeId。

每次进程启动生成 BootId，用于区分进程重启和计数器重置，不能替代 NodeId。握手报告协议版本、应用版本、插件能力摘要、启动时间与当前配置修订号。

生命周期：`PendingApproval -> Active -> Suspect -> Offline`，管理员可转入 `Draining` 或 `Revoked`。认证失败独立标为 `AuthenticationFailed`，不要把密钥错误伪装成普通离线。恢复连接后先对账，再恢复任务。

默认心跳建议 10 秒，连续 3 次失败进入 Suspect，60 秒无成功通信进入 Offline；可配置，且不根据单次超时立即删除节点。节点撤销后拒绝新通信及写任务，停止下发，保留审计和历史状态。

当前已接入观察生命周期子集：`Distribution.HeartbeatIntervalSeconds`（1至300，默认10）、`SuspectFailureThreshold`（1至100，默认3）、`OfflineTimeoutSeconds`（10至3600且不小于心跳间隔，默认60）。首次观察前为 `Connecting`；成功为 `Active`，失败达到阈值为 `Suspect`，超过无成功通信期限为 `Offline`；HTTP 401/403独立标记 `AuthenticationFailed`。失败或过期快照不进入实时汇总，旧快照保留供诊断；取消采集不覆盖成功观察。此状态不等于持久注册审批、Draining/Revoked 管理或重入对账，这些仍需单独实现验收。后台采集在每轮完成后等待配置间隔，慢请求会增加实际轮询周期。

第一阶段手工登记 NodeId、地址、角色、复制组和独立密钥。第二阶段可增加一次性短效注册令牌和人工审批；禁止自动信任首次发现的节点。

准入配置增量：`NodeCommunication.Peers.<NodeId>.AdmissionState` 支持精确值 `PendingApproval`、`Active`、`Draining`、`Revoked`。显式登记的 Peer 默认 `Active`，未知 Peer 仍拒绝，配置非法状态启动失败。`Enabled=false` 优先拒绝所有通信。

- `PendingApproval` 仅允许已签名且明确授权的 `node.handshake`，不会凭握手自动批准。
- `Active` 仍须通过原有密钥、操作和运行状态域/组授权，不额外授予权限。
- `Draining` 只允许握手、状态/看板读取、既有命令结果查询和回滚；新 prepare/commit、状态复制及插件业务消息不允许。必须先确认未完成任务处理策略再排空，不能用排空替代回滚。
- `Revoked` 拒绝包括握手和查询在内的通信。不会撤销已经执行的远端副作用，也不会终止已经进入执行阶段的请求。

配置通信发送端在创建HTTP客户端及写入新Outbox前检查准入，接收端在签名验证后检查。旧版配置签名没有发送者身份；当通信已启用且任一Peer非Active或已禁用时，旧版配置接收入口整体拒绝，避免按Peer限制被旧协议绕过。运维应迁移到v2并关闭 `AllowLegacyProtocol`。

此增量是配置驱动的准入限制，不等于持久审批管理API、跨机器克隆身份冲突检测、恢复连接前对账或在途任务完全排空已实现。相关验收仍需完成。

生产对账接线增量：Controller启用通信和Distribution时，`NodeHandshakeMonitor` 每轮完成后等待10秒，以最多4个并行目标执行签名握手，单目标40秒预算。只有启用v2、配置了 `node.handshake` 权限的登记节点参与。观察元信息变化、失联或Controller重启后必须重新核对既有Outbox结果、节点状态与最新握手；不会自动推进暂停的部署。

生产注入的 `DistributionNodeClient` 在新prepare/commit及实际命令发送前检查登记观察门控；未Ready、观察过期或身份冲突时拒绝。既有命令结果查询与rollback仍需独立权限，但不受新任务门控阻挡。该机制不取消已发送请求，不将未知结果变成未执行，也不会让旧v1协议获得v2登记保证。

Prepared重连不是直接放行，也不是永久拒绝：Controller必须有唯一匹配节点、集群、部署ID的未归档持久prepare记录，重新查询远端prepare结果获得匹配ACK，并核对状态、握手元信息及核对前后Outbox证据未变化，才能恢复Ready。已有NACK、缺失记录或核对过程中记录变化均不放行。恢复服务不发送commit，是否继续仍由原部署/管理员控制；候选过期与节点本地提交前校验仍生效。

管理员可通过 `GET /api/distribution/nodes/{nodeId}/identity` 查看登记；`POST /api/distribution/nodes/{nodeId}/identity/confirm` 确认已观察到的身份冲突，提交 `requestId`、`observationId`、`acceptedBootId`、`retiredBootId` 和 `reason`。接口要求管理员身份，保留确认人及理由，重复请求保持幂等；过期观察或未见过的BootId不能被确认。确认后仍需新握手与对账，不能直接开启任务。身份冲突确认只针对启动实例，不自动批准PendingApproval节点。

## 5. 认证与防重放

第一阶段采用 TLS + 每节点独立 HMAC-SHA256 凭据，后续可选 mTLS。不能使用控制台密码作为节点密钥；生产建议随机生成至少 32 字节密钥。控制端到节点使用节点专属密钥；Peer 使用逐对或明确方向的凭据，避免一个节点失陷冒充整个集群。

新签名的规范串固定用 LF，UTF-8 编码：

```text
protocolVersion
HTTP_METHOD
canonicalPath
clusterId
senderNodeId
receiverNodeId
keyId
unixSeconds
nonce
sha256(rawBodyBytes)
```

agent v2 不允许查询参数，方法固定大写，路径采用注册的固定规范路径；拒绝别名、重复斜线及编码歧义。摘要针对收到的原始 JSON 字节，不能反序列化后重新序列化再验签。签名请求禁止 HTTP 自动跳转，避免凭据或正文发往未授权主机。

验签后再进行业务授权：Controller 可分发配置，普通 Node 仅能上报自己的状态及向授权复制组发送许可域的数据。签名有效不代表拥有全部权限。

Nonce 为至少 128 位随机值。按 `(sender, keyId, nonce)` 做原子占用，存放在持久 TTL 表，保留时间覆盖请求允许时间窗和未来时钟偏差。过载或防重放存储不可写时拒绝机器写请求，不降级为无保护模式。第一阶段单进程唯一写入；多进程或多控制实例必须共享原子防重放存储，否则禁止部署成一个逻辑身份。

KeyId 支持新旧密钥短时重叠，发送方切换后撤销旧密钥。后台仅能覆盖密钥，不回读明文，日志不记录签名、密钥、配置正文和敏感插件字段。

重试使用新 timestamp/nonce/signature，但保持相同业务 MessageId。防重放与业务幂等分别处理，不可混用。

## 6. 消息契约与错误

新增契约建议使用 `/api/v2/node-agent/{operation}`。v1 接口保持原有解析语义，禁止在同一个路径上静默改变签名规则。

```json
{
  "protocolVersion": 2,
  "clusterId": "cluster-a",
  "senderNodeId": "control-01",
  "receiverNodeId": "edge-01",
  "messageId": "d02c75a3-2b33-4e63-891e-247f1fe3373e",
  "correlationId": "deployment-20261019-001",
  "type": "configuration.prepare",
  "createdAt": "2026-10-19T02:00:00Z",
  "expiresAt": "2026-10-19T02:05:00Z",
  "payload": {}
}
```

消息类型、签名路径、发送者身份必须匹配。过期命令不得开始执行；已经受理的操作按任务状态查询，不因重试时间戳更新而延长业务有效期。

响应包含 `messageId`、`operationId`、`status`、`errorCode`、`messageKey`、`messageArgs`、`retryable` 和 `traceId`。状态区分 Accepted、Succeeded、Rejected、InProgress、Unknown；Accepted 只表示已持久接收，不表示已执行成功。

协议状态及错误码始终使用稳定英文标识，用户可见文案由前端按语言资源渲染。插件错误由插件自带资源解释；缺少资源时回退到可读错误码，不把服务器语言固定为用户界面语言，也不翻译用户输入的路径、节点名或配置值。

HTTP 状态约定：401 身份无效，403 越权，409 幂等冲突或基准版本冲突，413 过大，422 业务配置不合法，429 限流，503 临时不可用。保留结构化错误响应，不单纯调用 EnsureSuccessStatusCode 后丢弃错误明细。

## 7. 可靠交付、背压与取消

采用至少一次投递和持久幂等，不宣称 exactly-once。

接收端幂等键为 `(cluster, sender, operation, messageId)`，记录正文摘要、执行状态和结果。同键同摘要返回已有结果；同键不同摘要返回409。受理状态必须先落盘，提交完成后持久结果；进程恢复时查询实际配置版本来修复中间态。

发送端配置命令写持久 Outbox，成功确认后完成；响应丢失视为 Unknown，先查询 operationId，不能直接视为失败后回滚。幂等结果至少保留7天；超过留存期的旧命令拒绝重放，改用新任务并重新检查基准版本。

默认建议：单次请求15秒、最多3次传输尝试、指数退避并加入随机抖动、遵守 Retry-After。只重试连接中断、429及明确的临时错误；401/403/409/422不自动重试。配置任务总时限与单次HTTP超时分开，不能因浏览器断开取消已经持久受理的部署。

每目标并发默认4，配置写操作每节点串行；状态同步与控制命令使用独立有界队列。队列按条数及字节数同时限额。配置任务满时拒绝受理，状态更新可按键合并并通过反熵修复，遥测可采样或丢弃并计数。

主动取消在通信层明确捕获，返回 Cancelled 结果，不记为节点故障、不继续重试。超时标记 TimedOut；若写请求可能已到达远端，状态为 Unknown。服务停止停止领取新任务，有限等待在途任务，保留未确认记录供下次恢复。

## 8. 配置分发与冲突

每个配置任务固定目标集合、不可变配置内容摘要、基准修订号和目标修订号。prepare 校验摘要、版本支持、配置语法、插件能力和节点专属覆盖规则。

不得直接把 Controller 自身的全部主配置复制到 Node：节点身份、Role、监听地址、证书路径、密钥、状态目录及本机上传目录属于节点本地配置。需要定义允许分发的配置清单和本地覆盖优先级；最终生效配置应在目标节点合成并校验。

推荐流程：创建任务并持久化 -> 逐节点 prepare -> 批次全部准备完成 -> commit -> 查询实际修订号与健康 -> 下一批。任一节点结果未知时先暂停批次并对账。已提交节点可补偿回滚，但回滚也可能失败，必须保留 RollbackFailed 状态及运维入口。

commit 必须验证当前修订号仍等于基准，防止覆盖操作员期间的本地修改。prepare 候选建议30分钟过期；过期清理前确认没有正在提交的任务。不同内容不得复用同一 deploymentId。

第一阶段只支持一个活动 Controller，禁止同时启动两个控制者写同一组节点。未来高可用必须引入外部一致性租约和单调 fencing token；节点拒绝低于已持久 token 的命令，不能仅靠心跳或静态优先级选主。

## 9. 运行状态与插件

保留 IRuntimeStateStore 和现有域模型，但增加域级复制策略及权限：

| 数据 | 推荐策略 | 边界 |
| --- | --- | --- |
| 动态封禁、白名单 | 有版本的最终一致状态、TTL、墓碑 | 跨节点传播存在窗口 |
| CC计数 | 节点分量合并，明确窗口、启动代次和重置语义 | 不承诺精确全局限流 |
| 验证码消费 | 内置 LyWaf 权威节点统一消费、持久序号与文件原子发布，无数据库 | 挑战不再异步复制；部署及持久化约束见 [共享验证码存储](38-共享验证码存储.md) |
| 插件幂等任务 | 允许重复的任务可复制状态；强语义任务用原子存储 | 不能把LWW当分布式锁 |
| 日志和指标 | 分批上报、保留来源及时间 | 不进入配置事务 |

复制增加每发送者序列、批次摘要、ACK游标和缺口检测；按分页增量补齐，游标过旧时交换快照。远端合并不重新广播相同事件，防止环路。序列必须跨重启持久，或以BootId区分计数代次。

墓碑不能仅按固定时间删除后允许任意旧节点直接回归。离线超过保留窗口的节点须先重新引导快照，并丢弃旧复制代次，再允许发送增量，防止删除数据复活。

插件使用宿主通信契约，声明可收发的消息类型、schema版本、目标组和权限；宿主统一认证、限额与审计。禁止插件自行读取其他节点密钥或发送任意目标地址。未安装插件或schema不兼容返回明确NACK，不执行动态代码下载。

当前已实现的插件节点消息服务及边界：

- SDK新增PluginPermission.NodeMessaging、PluginMetadata.NodeMessages、IPluginNodeMessageClient及IPluginNodeMessageHandler。每条能力声明精确MessageType、SchemaVersion、TargetGroups和CanSend/CanReceive，重复/不匹配声明拒绝。宿主检查插件Running、声明NodeMessaging且实际获授该权限，再检查本地PluginNodeMessages.Grants；普通Network权限不替代NodeMessaging。schema是精确协议版本协商，不是通用JSON Schema引擎；字段业务校验由handler负责，宿主限制JSON对象、深度16和64KiB。
- 插件从context.NodeMessages取得绑定自身ID的客户端，仅可传消息类型、schema、组、JSON数据、稳定小写UUID业务messageId和取消令牌。不能传其他PluginId、Endpoint、KeyId或签名密钥。宿主从PluginNodeMessages.Groups解析最多16个目标，从Distribution.Nodes选择已启用v2地址并使用NodeCommunication.Peers凭据，禁止重定向/协议降级；生产HTTPS源地址约束沿用节点传输规则。收端额外要求本机属于目标组且发送Peer在该插件AllowedSenders中。
- 固定外层operation为plugin.message，统一签名、原信封身份/期限、持久nonce防重放及AllowedOperations授权。NodeAdmissionPolicy控制双方准入，Draining/Revoked不接受新插件请求；不修改RuntimeState合并或sync。主线程已完成共享NodeCommunicationEndpoints/Operations接入；真实Kestrel HTTP测试通过正式AddPluginNodeMessaging注册和MapNodeCommunication路由验证成功ACK、缺插件404及schema不兼容422。
- 每次调用固定目标集合/Endpoint/正文摘要至groups日志，相同业务UUID改变正文或组成员/地址拒绝。每目标的实际MessageId由PluginId和业务UUID派生并持久防重；配置热变不能让同ID向新节点追加发送。每组最多4个并发传输，每服务总共16个发送/执行槽位；每Peer+Plugin+方向每UTC分钟最多60次，速率索引最多1024项并清除旧窗口。速率为内存固定窗口，重启会重置，不承诺集群全局配额或滑动窗口上限。
- 每次HTTP最多10秒，单次发送不自动重试；Unknown/丢响应不能用新UUID盲重发。接收先持久记录Unknown，再调用handler，成功后保存有界ACK/NACK；相同消息返回原记录，正文冲突409。执行异常、取消、落盘失败均不重执行。handler取消后不配合退出的任务继续占用槽位直到真实结束，不通过取消无限创建后台任务；本机恶意同步/死循环插件仍需要进程级隔离。
- NodeCommunication.StateDirectory/plugin-messages下groups、incoming、outgoing分别最多10000条和64MiB（计入临时替换），单记录最多16KiB；WriteThrough、Flush(true)、原子替换，执行/传输前存储失败不产生业务效果。独占消息锁覆盖执行、短全局锁覆盖配额与写入。审计只含原节点身份、插件/消息类型/schema/组、摘要、时间、Unknown或完成结果，不含Payload、密钥、签名或异常全文。记录/防重墓碑不自动删除，满时失败关闭；尚未提供此类Unknown人工核对、日志归档/迁移或持久投递重试。
- 缺插件/handler返回node_plugin_missing，schema不兼容返回node_plugin_schema_unsupported；不尝试拉取或加载代码。限额、权限、冲突和存储异常均有明确稳定NACK。历史已持久完成的重复信封可返回历史结果，不代表当前插件仍安装或正在执行。
- PluginContext.Services不再暴露根容器：封闭目录仅返回IServiceProvider（自身）、IPluginContext、插件配置快照IConfiguration、IPluginTaskCoordinator、IPluginStorage、IPluginNetworkClientFactory、绑定身份的IPluginNodeMessageClient及NLog.Logger。未知类型返回null，GetRequiredService抛错；Options/manager/PluginNodeMessageService、根配置、scope factory、IHttpClientFactory和IEnumerable包装不回退根容器。SensitiveConfiguration也只影响本插件配置快照，不授予节点密钥访问。已有能力接口保持兼容；任意自定义宿主服务解析不再支持，外部插件需迁移至经审查的类型化能力。
- 这不是进程内恶意代码沙箱：现有ILyWafPlugin.ConfigureServices/ConfigureMiddleware仍是受信宿主扩展入口；插件可反射对象私有字段、访问文件或自行创建HttpClient，现有GetPlugin亦返回其它插件实例。受限Services防止正常契约解析泄露，不证明恶意.NET代码无法获取密钥。强隔离需要独立进程和受限IPC，此阶段未实现。

节点消息配置示例（本地受控配置，不通过远端业务配置分发）：

```yaml
PluginNodeMessages:
  Enabled: true
  Groups:
    workers: [edge-a, edge-b]
  Grants:
    sample:
      SendGroups: [workers]
      ReceiveGroups: [workers]
      AllowedSenders: [controller]
Plugins:
  Permissions:
    sample: NodeMessaging
```

旧兼容模式双方还需配置NodeCommunication.Peers.<peer>.AllowedOperations包含plugin.message，发送端配置每个目标的Distribution.Nodes.<peer>.ProtocolVersion=2及Endpoint。插件自身能力也须声明workers及对应版本；以上配置不授予任意URL访问。

托管模式不配置节点间地址与密钥。节点只保留中控接入配置；中控中转需要在该插件的宿主授权中增加：

```yaml
PluginNodeMessages:
  Enabled: true
  Groups:
    workers: [edge-a, edge-b]
  Grants:
    sample:
      SendGroups: [workers]
      RelayGroups: [workers]
      AllowedSenders: [edge-a, edge-b]
```

目标节点仍需 `ReceiveGroups: [workers]`，以及包含原始来源的 `AllowedSenders`；发送节点需 `SendGroups`。中控需要安装并授予对应插件 NodeMessaging 权限及发送声明，但中转不调用中控插件 handler。来源字段由宿主生成，插件不能指定；普通节点不能伪造中控转发来源。中控到目标的持久回执使用原始来源和业务 ID 派生独立 ID，正文冲突拒绝，已知结果复用、未知结果不重发；断线不会回退节点 HTTP 直连。

### 9.1 多节点同时服务时的 CC 判定

本节为必须纳入实现的设计，不仅是控制台汇总需求。假设同一站点由 A、B、C 三个节点服务，规则为“同一客户端10秒内达到100次触发”：A收到40次、B收到35次、C收到30次，总计105次。只看单机计数会全部漏过；汇总数据必须能反馈到各节点的防护判定。

当前 `Services/Statistic/CcRuleChecker.cs` 已调用 IRuntimeStateStore 的 IncrementWindow/GetWindowValue，并同步 cc.triggered；不是完全没有跨节点计数。但目前主要以 rule.Id 和 clientIp 构造键，缺少显式站点隔离、规则版本及完整性说明，不能据此承诺精确全局阈值。

统一定义三条独立链路：

1. 请求节点本地实时计数和判定，不等待控制台轮询。
2. CC增量计数、封禁决定通过专用高优先级通道传播，接收后更新本地判定视图。
3. Controller汇总统计、决策和传播状态，供查询与告警；Controller离线不应停止默认模式的CC防护。

### 9.2 计数范围、身份和规则版本

每条规则显式声明 Scope：Node、SiteGroup 或 Cluster。默认采用 SiteGroup，跨节点共享同一业务的稳定 SiteId；不同站点不能仅因客户端IP相同互相处罚。Cluster级IP封禁必须由管理员显式选择。

建议计数键为：

```text
ClusterId / ProtectionGroupId / SiteId / RuleId / RuleRevision /
SubjectType / SubjectKey / MetricType / WindowStart / WindowSeconds
```

Subject可配置为客户端IP、可信登录账号或可信API凭据标识。默认使用归一化客户端IP，统一IPv4映射与IPv6表示。只从配置的可信代理链解析转发头；不能允许客户端伪造X-Forwarded-For绕过或栽赃封禁。未认证的账号字段不能直接当可信身份。

规则使用稳定ID和不可变Revision。阈值、匹配条件、动作或窗口改变均创建新Revision。灰度期间不同Revision的计数不相加，界面显示覆盖不完整；需要全组生效后再开启新版本的集群阈值判定。对已有封禁是否撤销必须作为发布策略明确选择，不能因Revision改变而意外绕过处罚。

每个外部请求只在指定的入口防护层计一次。内部回源重试、镜像请求及重复同步消息不增加入口访问计数；若节点形成多级代理，使用受认证的入口归属标记，不能信任外部提供的“已计数”头。业务客户端真正重发的请求仍属于新访问。

### 9.3 默认方案：异步汇总、本地执行

新增 ClusterApproximate 模式作为第一阶段推荐方案；不是现有配置选项。

每个计数键按 `(NodeId, CounterEpoch)` 保存单调递增分量。发送累计值而不是易重复的裸增量，接收端对同一分量取max，再对不同分量求和。同一份复制数据到达两次、乱序到达或经快照修复都不会重复计数。

CounterEpoch在计数源重建时生成并持久登记；旧进程分量保留到对应窗口结束，不把重启后从零开始的计数直接覆盖旧分量。过期窗口只保留诊断，不重新触发封禁；禁止接收远端消息时把TTL重新延长为完整窗口。

建议初始参数：最多250毫秒批量刷新一次，单批最多256KiB；阈值附近或首次封禁立即刷新。参数须通过压测确定，不是实时性保证。原有30秒反熵仅用于修复，不能作为10秒CC窗口的主要同步手段。计数采用有界按键合并缓冲，过载时上报缺失与延迟，不能静默把不完整计数当完整结果。

第一阶段统一使用UTC对齐固定窗口，保持现有窗口语义；明确固定窗口边界可能允许相邻窗口突发。未来滑动窗口需独立引入带版本的时间桶算法，不能把固定窗口结果标为精确滚动10秒统计。短窗口时钟要求应明显严于签名时间窗，例如偏差超过500毫秒进入降级，不因签名仍有效就认为计数窗口可比较。

任一节点合并后发现阈值已达到，可生成封禁决定；本地新请求读取最新汇总视图，也会执行同一规则。无新请求时后台合并仍可生成并广播决定。应避免每个复制包都重复写封禁日志。

异步模式存在在途请求和复制延迟，无法保证第100次恰好被所有节点同时拦截。超额量与同步延迟期间的请求速率及在途并发有关，没有固定的“最多多放几次”承诺。网络分区时继续本地防护，界面显示Degraded；可以配置更保守的本地阈值或人机验证，但不能把全局阈值简单除以节点数作为默认，否则流量不均会误封。

### 9.4 严格模式：中心原子判定

对于登录、短信、昂贵API等必须限制全局放行数的规则，后续可选 ClusterStrict 模式要求所有节点在放行前通过统一原子限流接口检查并消费额度。若实施，应由单一授权节点持久串行完成计数、阈值判断与有效期处理，不新增第三方数据库。当前尚未提供该精确限流模式，不能把验证码权威存储或异步CC计数当作其实现。

严格模式会引入请求热路径的网络依赖，不与默认异步模式的“完全本地判定”混淆。配置必须显式选择中心不可用时 FailClosed、Challenge 或 LocalFallback；LocalFallback 一旦触发就不能再宣称全局精确。

对中心调用的超时重试使用服务端生成的 AdmissionId 做短期原子去重，防止同一个请求因ACK丢失重复消耗额度。客户端自行重发获得新的AdmissionId。明确阈值规则是“达到阈值开始处罚”还是“允许N次、第N+1次拒绝”，测试和界面使用相同语义。

中心存储故障转移的数据丢失语义也属于严格模式边界；普通异步主从切换不能自动视为零丢失。安全要求不允许超额时须选择匹配的一致性保障并故障关闭。第一阶段不实现额度预分配，以免扩大计数与回收复杂度。

### 9.5 封禁传播、解封与日志去重

封禁记录包含ProtectionScope、RuleRevision、Subject、TriggerWindow、DecisionId、OriginNode、ObservedCount、Action、ExpiresAt和PolicyGeneration。多个节点对同一范围、规则、对象、触发窗口生成相同逻辑DecisionId，来源证据作为分量合并，不生成多条“新封禁”。

同一处罚期内继续命中只更新命中统计和最后命中时间，不重复新增封禁日志，也不默认续期。确需续期时显式定义续期规则和最大期限。临时黑名单不能无条件升级成全站点黑名单。

解封不是简单删除本地缓存：由授权控制端发布更高PolicyGeneration的解除记录并保留墓碑。旧代次的处罚和延迟包不得覆盖新代次解封。手动解封语义默认为“清除本代处罚，切换计数代次；此后新请求可以重新触发”，不等同永久白名单。已离线节点未收到新代次前仍可能执行旧处罚，控制台显示未确认节点，不能立即宣称全节点解封成功。

每节点维护自身执行状态和ACK，Controller展示“已执行2/3、1个节点离线”。离线节点恢复时先取得最新PolicyGeneration和有效处罚快照，再处理缓存增量。

CC页面保留最近1000条逻辑封禁记录，按DecisionId去重；另显示各节点拦截请求数、首次/最后命中与传播状态。1000条UI留存限制不用于截断有效封禁状态、幂等记录或审计保留期。

### 9.6 统计汇总的口径

| 指标 | 汇总方法 | 必须避免 |
| --- | --- | --- |
| 入口请求数、拦截数 | 按来源节点/计数代次/时间桶合并累计值再求和 | 把重复快照或已汇总的节点视图再次相加 |
| CC逻辑封禁次数 | DecisionId去重 | 多个执行节点各算一次封禁事件 |
| 实际拦截请求数 | 每节点真实拦截计数求和 | 与封禁决定数量混用 |
| 错误率、拦截率 | 汇总分子除以汇总分母，并统一统计窗口 | 直接平均节点百分比 |
| UV、独立攻击IP | 明确采用精确集合或可合并近似算法 | 把各节点去重数相加称为全局去重数 |
| 延迟分位数 | 合并兼容直方图桶后计算 | 平均各节点P95/P99 |
| 在线节点数、连接数 | 当前有效快照求和并标明时间 | 把离线缓存当实时数据 |

Controller统计接口必须同时返回统计窗口、预期节点集合版本、已覆盖节点、缺失节点、数据水位和Complete/Partial状态。缺失节点不是0；历史窗口中已收到的离线节点计数不因节点当前离线而丢弃。节点返回本节点原始分量和汇总判定值时使用不同字段，聚合器只对原始分量求和。

当前代理遥测实现：`NodeDashboardSnapshot.Telemetry`携带本地原始分钟桶，`MultiNodeDashboard.Telemetry`携带上一完整UTC分钟的合并结果。请求按代理管线完成时间归桶；错误为5xx或管线异常，拦截采用`LyWaf.Intercepted`标记，每次管线调用只记一次，回源重试不另计入口。比例取0到1；Partial时仅代表IncludedNodes，不能解释为全组。直方图Counts为非累计桶，最后一项是overflow，边界单位毫秒；P95/P99为合并后nearest-rank桶上界近似值，空样本或分位落在overflow返回null。启动残缺窗口、旧节点缺字段、不同schema/边界、无效计数/水位、已检测时钟偏差均显式排除并说明原因。

该实现不依赖Prometheus导出开关，不读取或平均节点分位数。节点内存保留当前及前三个分钟桶；控制端保留已收到的完整桶，离线缓存可贡献历史窗口但不冒充实时在线数据。统计挂点之前的拒绝（例如RequestDrain）、管理入口、TCP/UDP不在该schema口径内；不是全部网络入口请求数。跨启动的残缺桶不拼成完整窗口。长期持久历史、Controller重启水位恢复、通用UV和逻辑DecisionId统计仍需独立实现，旧Security累计字段未被冒充为新窗口指标。

UI使用独立的分钟窗口区域展示UTC起止、覆盖、缺失原因、数据水位、预期集合版本、原始分子/分母和近似P95/P99。旧Controller无Telemetry或未知schema显示不可用；旧节点缺Telemetry列为缺失，不以累计Security回填。零覆盖显示`-`而非0；有效空窗口请求数为0、比率/分位数为`-`；有样本但分位数落在overflow则显示`> 最大桶边界 ms`。

专项复测：`Frontend/scripts/test-node-telemetry-e2e.mjs`先运行两节点真实HTTP采集测试（10次错误/拦截、90次成功，汇总10/100=10%），将Controller原样JSON交给浏览器实际组件及MultiNode页面。脚本参数1可指定Playwright模块路径，参数2可指定已安装浏览器channel（如msedge）；输出位于`artifacts/node-telemetry-e2e`。覆盖中英文、390/1440宽度、完整/部分/直方图不兼容/零覆盖/旧Controller、未知schema及溢出分位数。HTTP测试使用测试agent路由，页面API以真实汇总JSON回放，不重复宣称鉴权端点或生产部署验收。

### 9.7 CC专项验收与实施优先级

CC异步计数与封禁传播进入P1，而不是等到普通报表完成后再考虑；其他域的增量复制优化仍可在P2推进。严格模式单独作为可选后端交付。

- A/B/C分别40/35/30次：同步后全组识别105次，生成一个逻辑封禁，各节点执行。
- 复制重试、乱序、ACK丢失：计数不膨胀，日志不重复。
- 两个站点相同IP：默认隔离；显式Cluster规则才共同计数。
- 规则灰度、节点重启、时间桶切换：不串版本、不丢掉尚有效旧分量、不把旧窗口算入新窗口。
- 同一封禁期连续请求：累计拦截数增长，逻辑封禁日志保持一条。
- 网络分区：异步模式明确显示Partial/Degraded，严格模式按故障策略执行。
- 解封后收到旧封禁消息：不复活旧代处罚；离线节点恢复先同步解封代次。
- 入口后重试三次回源：入口计数仍为一次；真正三次客户端请求计为三次。
- 多节点百分比、UV和分位数：使用正确聚合口径并标注近似值。
- 1秒短窗口、时钟偏差、高基数IP攻击和复制队列饱和：评估实际漏拦窗口、内存上限和降级行为。

## 10. 配置草案

### 10.1 已接入的v2配置分发子集

当前实现新增 `/api/v2/node-agent/configuration.prepare`、`configuration.commit`、`configuration.rollback`、`configuration.result`、`node.status`、`node.dashboard`。请求采用第6节消息信封，响应暂时沿用对应业务结果。配置命令已接入持久Inbox：先记录接收，再执行并记录ACK/NACK；相同发送者和MessageId重试返回原结果，不同业务内容返回409。客户端按集群、发送者、接收者、操作和DeploymentId生成稳定MessageId，重发时使用新nonce。执行中断留下的记录先核对磁盘任务状态：同任务的Prepared/Applied可确认prepare（还需候选内容完全匹配），Applied可确认commit，RolledBack可确认rollback。确认后补写Inbox结果；缺少证据仍返回 `node_outcome_unknown`，不会自动重放副作用。Inbox通过独占文件锁串行执行，忙时返回503，当前上限10000条且尚未自动清理。Outbox已接入，详见下节；配置落盘与任务状态落盘之间的完整崩溃恢复、Inbox保留策略及统一成功响应仍待实现。RuntimeState不得以此宣称全部通信已迁移v2。

`NodeCommunication` 已支持 Enabled、ClusterId、NodeId、Role、RequireHttps、AllowLegacyProtocol、StateDirectory、MaxMessageBytes、AllowedClockSkewSeconds、Peers。Peer已支持 Enabled、Role、ActiveKeyId、Keys、AllowedOperations。Keys是密钥版本到密钥值的映射，至少32字节；保密配置中设置，禁止使用示例短密码。SecretReference尚未实现。

选择v2的发送端同时配置 `Distribution.Nodes.<目标>.ProtocolVersion = 2` 和对应Endpoint，并在NodeCommunication.Peers登记目标和ActiveKeyId；接收端在Peers登记发送者、密钥版本以及允许的操作。双方ClusterId相同，各自NodeId唯一。发送方Peer的Role表示目标角色，接收方Peer的Role表示发送方角色。

生产RequireHttps保持true；端点必须为不含用户信息、查询串和额外路径的HTTPS源地址。AllowLegacyProtocol默认true以兼容升级；设置false会禁用旧配置分发和旧RuntimeState协议的发送与接收。必须为每个需要继续同步的Peer显式选择v2并配置身份和授权，不存在失败后自动回退旧签名的行为。

配置命令只允许Controller发送给Node；所有操作还须出现在接收方为发送者配置的AllowedOperations中。签名绑定集群、双方NodeId、密钥版本、固定POST路径及原始正文摘要；业务消息另校验过期时间。轮换时先在接收端加入新KeyId，再切换发送端ActiveKeyId，观察后删除旧KeyId。

### 10.1.1 已实现的配置Outbox及边界

- `DistributionNodeClient` 的v2 prepare/commit/rollback实际经过 `NodeCommandOutbox`，首次HTTP前持久保存原始信封、目标Endpoint、尝试次数和状态；结果校验通过后保存ACK或NACK。采用独占文件锁、WriteThrough、Flush(true)、临时文件替换；磁盘错误拒绝继续发送。记录不保存传输密钥，但prepare含配置正文，StateDirectory必须按敏感配置限制访问。
- 稳定业务MessageId和原始CreatedAt/ExpiresAt跨客户端重建保留；相同ID不同正文或Endpoint拒绝。Completed重复调用返回本地持久结果，不再发HTTP；不得手工删除记录后重用旧DeploymentId。
- 总期限固定5分钟，最多3次传输（首次命令加最多2次只读核对），次数在发出前落盘，重启和重复调用不能重置。单次仍使用Distribution.RequestTimeoutSeconds的1至120秒限制，同时受总期限约束。暂未增加可配置Outbox参数。
- 网络异常、单次超时及HTTP 408/429/502/503/504进入有界核对重试；指数退避从250毫秒开始并加0至249毫秒抖动，持久保存NextAttemptAt，取Retry-After和本地退避中的较大值，不越过总期限继续发送。401/403/409/422以及其他非临时HTTP错误不重试；首次拒绝记Rejected，核对被拒绝记Stopped（不代表原命令执行失败）。正文损坏、过大或ACK身份不匹配直接抛错，保留Unknown供显式核对。
- 一旦持久记下发送尝试，即使无法确定请求是否到达，也不自动重发业务命令。后续 `configuration.result` 的Payload携带原始信封，外层查询有自己的MessageId，每次传输重新生成timestamp/nonce/signature。接收端只查询对应Inbox并尝试业务状态对账，绝不新建接收记录或调用配置执行。没有记录或无法确认返回409并停止；这会保守牺牲自动恢复成功率，不承诺至少一次最终送达。
- 接收端必须为Controller显式授权 `configuration.result`，仍要求Controller到Node角色和集群/双方身份绑定。旧节点不支持该路由时停止，不回退v1或重发命令。需先升级接收端并授权，再使用发送端恢复功能。
- `IDistributionNodeClient.ReadOutbox()`返回持久记录快照；`RecoverAsync(messageId, token)`恢复单条已尝试记录，只做只读核对或返回持久结果，仍受剩余次数/原期限约束。未尝试Pending记录要求显式业务恢复，过期或耗尽预算不自动重新执行；恢复时还在文件锁内检查记录必须存在且已尝试，防止记录删除竞态退回首次发送。恢复不是HTTP管理接口。
- `AddLyWafDistribution`已注册 `NodeOutboxRecoveryService`，NodeCommunication启用且Role为Controller时，启动后台立即扫描，之后扫描间隔5秒，不等待在途网络整批完成。只领取当前ClusterId/SenderNodeId的Unknown配置记录，要求已有发送尝试、尚有预算、未过期且NextAttemptAt已到；最多4个Peer worker，同Peer串行调用RecoverAsync，仅查询结果，不重新执行命令，也不重置原期限/次数。不建立无界等待任务队列，未领取记录留待后续扫描。不依赖页面或人工调用。RecoveryService只更新Outbox结果，不回填Controller状态，不推进或回滚部署批次。
- 停机取消后台服务令牌，停止领取并取消在途HTTP或退避，等待worker退出；已落盘次数和Unknown状态保留，下次启动仍受原预算约束。Completed、Rejected、Stopped、Pending、过期、预算耗尽的记录每轮直接跳过，不调用恢复、不输出逐条日志。扫描不是忙循环。磁盘忙/损坏、配置错误和恢复异常的警告整个服务最多每分钟一条，只记录异常类型，不输出配置或远端错误正文；存储读取失败本轮不发送，下一轮重试读取。安全归档边界见10.1.3。
- 调用取消立即停止后续重试，不删除持久记录；已发请求可能仍执行，保持Unknown。Outbox使用两级文件锁：`peer-locks/<cluster+receiver摘要>.lock`覆盖同一目标的发送/退避/结果更新，跨客户端实例及进程互斥；其他目标可并行。同Peer竞争快速抛IOException，既不发送也不增加/重置次数，后续调用重新读取持久预算。Peer锁文件不主动删除，避免删除与新持有者竞争导致锁失效；文件存在不表示仍被锁定，进程退出由操作系统释放句柄。
- 全局 `.lock`只覆盖目录快照、记录读取、配额检查和原子落盘，不跨HTTP或退避持有。锁顺序固定为Peer后全局，快照只取全局锁。每次新建或结果更新均在全局锁内核对条数/字节配额，包含旧记录和替换临时文件，避免并发准入或ACK增长突破上限。全局共享冲突最多等待5秒、每10毫秒重试；异步等待支持调用取消，权限/其他磁盘错误不循环重试。已返回的网络结果落盘不因调用者取消而省略，但锁等待仍有界。写失败清理本次临时文件并释放锁，原记录保持权威；落盘失败可能留下Unknown，不能因此重执行命令。
- 慢Peer不会阻塞其他空闲worker；新扫描可利用空闲槽位，不受上一轮慢请求阻塞。4个慢Peer同时占满槽位时其他Peer仍需等待，不承诺实时调度。正常发送和后台恢复共享持久Peer锁，竞争不会重置预算。
- 活跃目录最多10000条、64MiB（写入时包含旧记录与替换临时文件），满时拒绝受理/更新，不静默丢弃未知结果。存储故障后可能远端完成而本地仍Unknown，必须核对。到期后人工处理需先确认远端任务状态，不能删文件后盲目重放。
- Rejected/Stopped持久保存StatusCode和受限ASCII的ErrorCode、MessageKey、RemoteTraceId；前三者长度上限分别为128、140（含node.errors.前缀）、128。另保留类型为TimeSpan的RetryAfter。重启后重复调用和RecoverAsync恢复这些HttpRequestException.Data键，不发网络。其他Data、异常正文、远端响应全文不保存；旧记录缺少字段仍可读取。
- v1、status/dashboard和运行状态复制不经过此Outbox。过期人工核对管理API见10.1.5；前端管理界面及文件系统断电一致性验证仍未完成。后台传输恢复不等于部署自动续跑；Controller结果回填由其独立流程负责。

### 10.1.2 已实现的节点本地配置保护

`DistributionNodeService` 的prepare/commit/rollback共用 `NodeLocalConfigurationOverlay`，v1/v2均生效，不依赖Controller过滤。采用保守允许清单：只有 `ReverseProxy`、`Protect`、`Statistic`、`SpeedLimit`、`SimpleRes`、`ABTest`、`RequestMirroring` 是可分发业务节；其中 `Protect.CheckArgsFile`、`Protect.CheckPostFile` 仍取本地值。这些业务节采用候选全量替换语义，不是字段补丁，候选省略的业务节会删除。

其他节全部取当前节点主文件的值，候选不能新增、覆盖或删除，包括整个 `NodeCommunication`（身份、集群、密钥、Peers和权限）、`Distribution`（身份、角色、Nodes端点、Secret、权限和状态目录）、`RuntimeState`、`WafInfos`（监听及证书）、`FileServer`（本机文件/上传目录）、插件、日志、数据库以及未知扩展节。本地没有某个本地节时，Controller同名节也不会被复制。配置键按大小写不敏感处理，拒绝大小写重复和不支持的冒号展开键，避免伪装绕过。新业务节必须显式审查后加入允许清单。

实际格式及语义边界：

- 支持主文件扩展名 `.ly`、`.yaml`、`.yml`；请求Content按目标主文件格式解析，不做跨格式转换，其他扩展名拒绝。YAML使用现有YamlDotNet解析为结构，保留映射和数组，再校验合成结果；不进行文本拼接或正则替换配置字段。
- `.ly`使用现有LyConfigParser及LyToAppSettingsConverter。变量、条件和片段在prepare时解析，输出规范化静态块；注释、原始排版、变量定义和片段定义不保留。环境变量按当前进程解析；未解析且形似变量的字符串拒绝，防止后续重解析改变语义。不支持自定义LyConfigSource.Variables注入的额外变量契约，部署前应物化为主文件值。规范化会将本地已解析密钥写入合成文件，必须限制配置、版本库和StateDirectory的访问权限。
- `.ly`站点简写允许更换上游和路由，但转换后所有非业务键必须与本地完全相同。隐式新增/删除监听、变更证书或文件服务目录等会NACK，需先在节点本地预置；不承诺任意Controller站点拓扑能直接套用。`import`在本地主文件和远端候选中均禁止，且在解析前拒绝，避免prepare读取任意导入文件。对象数组、null及无法无损重写的特殊键/结构目前拒绝；最终重解析的有效配置必须与预期合成字典一致，不能悄悄降级。
- 只合成主文件，不修改环境变量、命令行、补丁等额外配置提供者；它们仍按既有加载优先级生效。本功能不是任意插件字段的安全沙箱，也不自动管理本地文件或上传内容。

prepare保留原始请求及其Source摘要用于消息幂等，另写 `prepared/<deploymentId>.json.overlay`，并在节点状态保存EffectiveHash和本地主文件字节基准。合成候选先做语法及生命周期规则校验。commit只写该已校验合成候选；原始请求、合成摘要、当前基准及重新合成结果都须匹配。重启后从磁盘继续核对；合成文件缺失/篡改、旧Prepared状态没有EffectiveHash或本地已变化时拒绝提交，需撤销待提交任务并创建新任务，不能退回原文全量覆盖。

commit响应丢失或状态落盘中断时，核对使用合成内容、EffectiveHash、版本归档和当前主文件，不再将Controller原文摘要误当节点实际版本摘要。prepare重复请求仍比较原始请求。rollback取历史业务配置与**当前**节点本地配置重新合成，并使用基准条件写入，因此部署后本地换钥不会被补偿回滚撤销。文件写入后的重载失败恢复也使用条件写入，避免覆盖期间的新本地编辑。业务字段自身的回滚冲突策略、候选自动清理和完整断电恢复不由本节承诺。

### 10.1.3 Outbox安全保留与归档

- 只归档已持久确认ACK/NACK的Completed记录，且CompletedAt不早于CreatedAt、已满7天。Unknown（包括过期及预算耗尽）、Pending、Stopped、Rejected和缺少完成时间的旧记录不会自动删除。Stopped/Rejected不视为已确认业务结果，期限结束也不等于执行失败。
- 归档写入outbox/archive，保留身份、Endpoint、原正文摘要、结果、次数和时间，移除原配置Payload。采用WriteThrough、Flush(true)、原子替换，成功后才删活跃文件。崩溃留下双份时读快照以归档为准，下次维护核对一致后删源文件；冲突或损坏失败关闭，不重发。
- 归档是永久防重放记录，不自动删除。相同业务调用校验原摘要后返回结果，内容不同拒绝；RecoverAsync只返回归档结果。ReadOutbox仍包含归档结果，但其Payload为null，不能作为重新执行的配置来源。
- 后台启动扫描后自动维护，之后至多每小时一次（失败也等待下个周期），每次最多归档100条；忙Peer跳过。维护沿用Peer后全局锁顺序，停机取消不破坏先归档后删除顺序。日志使用服务级每分钟一次节流，不逐条输出。
- 活跃目录与归档目录分别限制10000条、64MiB，写入包含替换临时文件。归档满或写失败保留源记录，不丢结果；因此不是无限磁盘回收方案，长期运行仍需受控迁移/管理流程。结果本身可能含敏感信息，归档也须限制访问权限。
- 不实现Unknown自动清理、人工裁决界面或完整断电一致性证明。不得独立删除Outbox归档/Inbox后复用旧DeploymentId，否则会破坏幂等保证；不能据此盲目重放。

### 10.1.4 节点候选期限与Inbox保留

- 新prepare成功时将CandidateExpiresAt固定为节点UTC时间加30分钟，保存在Distribution.StateDirectory/node-state.json；重复prepare、重启和查询均不续期。它独立于单条消息的5分钟传输期限。commit在状态检查和写入前检查到期，过期不能开始提交。旧Prepared缺少期限时拒绝commit且保留资料，不按mtime推测期限，需核对后撤销并创建新任务。
- commit首次可能修改配置前先持久写CommitStarted标记；此后异常向上传播，Inbox保持Unknown而不是把不确定结果保存成NACK。结果不明时禁止直接再次commit或当作未提交候选rollback。核对仍可依据候选、有效摘要、版本档案及当前文件确认Applied，即使此时已超过候选期限。清理不触碰该未知提交的候选，也不删除Applied/RolledBack的版本或补偿信息。
- 候选清理与prepare/commit/rollback共用NodeService的进程内互斥锁，仅将有明确期限、已过期且未开始commit的当前Prepared置为Expired。先持久写prepared/<deploymentId>.json.expired永久墓碑，再持久发布Expired状态，最后删除原请求及overlay正文；墓碑始终保留，不能复用旧任务ID。删除失败/崩溃保留墓碑并可在后续维护继续；墓碑损坏、磁盘或状态写失败不猜测业务结果。节点状态只在WriteThrough、Flush(true)、原子替换成功后更新内存。
- 保守边界：没有期限的旧候选、写入中断留下的孤立文件、已撤销候选、已应用和未知提交的证据不自动删除。仅当前明确未提交的过期候选和已持久标为过期的残留正文可清理；不是通用版本库GC。单逻辑节点仍要求单进程唯一写入，进程内锁不构成跨进程节点事务保证。
- Inbox在确认执行或核对结果时持久保存CompletedAt。完整ACK/NACK至少保留7天，此后在原路径原子压缩为Digest、CompletedAt、Retired墓碑，去除Result正文。旧记录没有CompletedAt以及Result为空的Unknown永不自动压缩/删除。墓碑仍计入10000条配额，不删除以腾出准入空间；满时继续失败关闭，需要后续受控迁移策略。
- 命中墓碑且摘要相同返回409 node_result_retired，不execute、不reconcile；不同正文返回node_message_conflict。查询和普通重试都不能把墓碑当作缺失记录。没有既存记录的过期命令在Inbox内也返回409 node_message_expired，不执行；已确认结果仍可幂等读取。过期、Unknown或退休结果均不能作为盲目重放依据。
- AddLyWafDistribution注册NodeConfigurationMaintenanceService。启用的v1 Distribution Node或v2 Node启动后立即检查候选，之后每分钟检查；启用v2 Node的Inbox启动后维护、之后每小时最多一次（失败也不忙重试），每轮最多压缩100条；候选正文每轮最多删除100组。Inbox维护与执行使用同一个文件锁，忙时不抢占执行；异常日志整个服务每分钟最多一条，仅记录异常类型。
- 停机取消维护等待和读取、停止下一条领取；原子落盘可完成当前文件写入，不会中途删除幂等墓碑。未实现自动裁决Unknown、跨存储原子事务、墓碑无限回收或完整断电故障证明；不得手工删Inbox/过期墓碑后复用旧MessageId或DeploymentId。

### 10.1.5 过期与预算耗尽的人工核对入口

`NodeReconciliationService`独立于Controller。需要Distribution与NodeCommunication均启用且为Controller；所有入口声明system.manage权限，同时按Distribution.Permissions.GlobalOperators/NodeOperators限制目标节点（沿用空权限配置的单管理员兼容规则）。身份取已认证的Username，不能在正文指定操作人；写入口不豁免既有step-up验证。没有配置正文、密钥或远端错误全文的返回入口。

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| GET | /api/v1/distribution/reconciliation/{nodeId}?offset=0&limit=50 | 当前身份所属、未归档的配置Outbox摘要列表；limit为1至100 |
| GET | /api/v1/distribution/reconciliation/{nodeId}/{messageId} | 原cluster/sender/receiver/message/deployment/stage、正文摘要、Endpoint、原期限/次数、Outbox结果摘要及独立人工核对日志 |
| POST | /api/v1/distribution/reconciliation/{nodeId}/{messageId}/query | 显式单次configuration.result查询，不发送prepare/commit/rollback |
| POST | /api/v1/distribution/reconciliation/{nodeId}/{messageId}/assessment | 记录人工判断，不发送任何节点请求 |

POST正文必须包含新的小写D格式UUID requestId、GET返回的digest、1至512字符且无控制字符的reason。query不允许assessment；人工判断额外提供assessment，枚举为Unresolved、OperatorBelievesApplied、OperatorBelievesNotApplied、NeedsIntervention。例如：

```json
{
  "requestId": "b8a38948-7941-4144-8d73-d940ca7b64f4",
  "digest": "从详情复制的64位原消息摘要",
  "reason": "工单OPS-123，核对节点当前修订号",
  "assessment": "NeedsIntervention"
}
```

- 只允许已有发送尝试且无确认结果的Stopped，或已过期/耗尽自动预算的Unknown进入操作。Pending、首次Rejected、Completed、归档记录及仍可自动恢复的Unknown不能借此执行查询。RequiresReview只反映该源状态，实际动作还检查人工日志预算。列表不展开日志，详情返回日志。原摘要基于Type、CorrelationId、Payload，与Outbox幂等摘要一致，调用者不能提供替代信封或任意Endpoint。
- 人工查询独立于自动重试：原Outbox次数/期限完全不变；每次人工动作只发一次请求，不重试，包括401/403/409/422。外层query新MessageId/timestamp/nonce，内层原信封和业务MessageId保持不变；仍校验v2凭据、Endpoint未变化及返回NodeId/DeploymentId/Stage。接收端可能核对并落盘已有操作结果，但绝不执行缺失命令。每次HTTP受既有1至120秒RequestTimeoutSeconds约束。
- 原命令每分钟最多一次人工query，永久最多10次；人工判断和查询合计最多100条。相同requestId、动作、操作人及内容重复提交返回已持久记录，不重新查询；同ID不同内容409。崩溃留下Requested也不自动恢复查询。需要再次检查时必须使用新requestId并受剩余人工预算约束，不能靠删日志重置。
- 日志位于NodeCommunication.StateDirectory/reconciliation，按完整原身份摘要分文件。每个命令持独占锁，网络期间不持全局配额锁，不阻塞其他命令。首次意图包含原身份/摘要、操作人、来源IP、reason和时间，必须WriteThrough、Flush(true)、原子替换成功后才发HTTP；返回后独立记录Observed、Unconfirmed或Cancelled。取消也尝试保存审计；保存失败保留Requested，不假装已确认。
- ObservedNodeResult仅表示本次收到的节点ACK/NACK及有界修订号，不写回Outbox、不喂给Controller自动结果回填。人工Assessment永远没有ObservedNodeResult，不能伪装成节点ACK。远端错误只保留受限错误码、trace及HTTP状态，不保存正文。reason是人员输入的审计说明，不应填写配置或密钥。
- 日志最多10000个命令文件、64MiB（含替换临时文件），单文件最多1MiB；满、损坏、锁忙或不可写均失败关闭。日志长期保留，不自动删除，非篡改证明/WORM审计；维护人员须保护目录权限。原Outbox归档后当前入口不提供归档日志浏览，文件仍保留。
- 409缺失/Unknown/退休结果、HTTP失败或人工“认为未应用”都不证明远端没有执行。操作者须结合节点当前配置、版本链和外部证据裁决；本阶段没有清除Inbox、重置预算、重新执行旧命令、强制标记节点成功、恢复部署或回滚接口。业务恢复需另行审批并重新检查当前基准，使用新任务不能被当作自动避开Unknown的手段。前端核对页面、人工预算扩容审批、日志迁移与Controller人工状态回填均未实现。

### 10.2 后续目标模型

以下为拟新增模型的示意，不可直接放入当前 config.ly 使用。字段解析与密钥引用机制属于后续实现。

```ly
NodeCommunication {
    Enabled = true
    ClusterId = "cluster-a"
    NodeId = "edge-01"
    Role = "Node"
    ProtocolVersion = 2
    StateDirectory = ".lywaf-node-communication"
    RequireHttps = true
    HeartbeatSeconds = 10
    OfflineAfterSeconds = 60
    RequestTimeoutSeconds = 15
    MaxConcurrentPerPeer = 4
    QueueCapacity = 10000
    MaxQueuedBytes = 67108864
    AllowedClockSkewSeconds = 60
    Peers {
        control-01 {
            Endpoint = "https://control.internal:7030"
            Role = "Controller"
            KeyId = "key-2026-10"
            SecretReference = "env:LYWAF_CONTROL_NODE_SECRET"
            AllowedOperations = ["configuration.prepare", "configuration.commit", "configuration.rollback", "node.status"]
        }
    }
}
```

本例是Node接收Controller命令的信任配置；Controller一侧登记edge-01及对应凭据。Peer复制另行显式授权，不能从Controller权限继承。实际配置应校验重复NodeId、非法角色、非HTTPS地址、未知权限、无效引用、队列上限和冲突的旧配置。

## 11. 模块与可观测性

新增 `Services/NodeCommunication`，建议包含 NodeIdentity、PeerRegistry、NodeTransport、NodeAuthenticator、MessageInbox、MessageOutbox、NodeHeartbeatService。业务服务通过类型化接口调用，不直接拼接URL或读取密钥。

DistributionNodeClient 和 RuntimeStateReplicator 分阶段迁移到该层；原业务配置应用、合并算法不随传输重构同时重写。前端保留 MultiNode 页面，增加身份、最后通信时间、期望/实际修订号、队列积压、最近错误码与待对账任务。

记录请求耗时、消息大小、重试数、队列深度、丢弃数、幂等命中、验签拒绝、状态复制延迟、部署Unknown数。指标标签只使用受控节点ID、操作类型和结果，不能放messageId、IP或路径等高基数字段。

审计记录操作者、源/目标节点、任务ID、摘要、修订号和结果；配置和密钥不入日志。健康快照与事件必须携带来源节点、BootId、采集时间；过期缓存不得算作实时在线数据。

## 12. 实施顺序与验收

1. P0：统一身份、错误契约、认证公共组件、签名测试向量；修复现有幂等摘要和结果未知处理。保留v1。
2. P1：持久Inbox/Outbox、队列隔离、后台心跳、v2配置分发、节点本地覆盖与版本冲突保护。
3. P2：运行状态分页增量、游标和快照引导、插件消息能力声明。
4. P3：按实际需求加入长轮询、mTLS和外部协调存储；多Controller高可用单独设计并验证。

验收至少覆盖：

- 1 Controller + 2 Node，Windows/Linux跨平台，正常分发及状态传播。
- 中文/英文控制台收到同一错误码时按各自语言显示，不依赖远端语言。
- 错误密钥、越权节点、跨集群消息、过期签名、正文篡改、重复nonce、重启后重放全部拒绝。
- 同消息同正文幂等、同消息不同正文冲突、ACK丢失后查询不重复执行。
- prepare后崩溃、配置写入后状态落盘前崩溃、部分commit及回滚失败都可恢复或明确转人工处理。
- 客户端取消、服务停止、超时分别分类；没有未观察任务异常和配额泄漏。
- 队列满、大正文、慢节点不会阻塞代理热路径；内存和磁盘增长有界。
- 长期离线后重新加入不复活已删除状态，不重复消费安全挑战。
- 本地配置变更导致基准冲突，不被远程任务静默覆盖。
- 协议不兼容明确拒绝写入；升级失败可退回v1，禁止自动降级弱化认证。

迁移按Controller先支持双协议、Node灰度升级、显式选择v2、观察稳定后停用v1执行。新旧协议不能同时提交同一节点上的同一配置任务。现有Distribution/RuntimeState配置由兼容适配器读取，不能直接删除旧字段。

## 13. 待确认项

默认按私网互通、3至20节点测试目标、单Controller落地。正式实施前确认是否必须跨公网/NAT、是否要求跨节点精确验证码单次消费、是否需要高可用Controller。这三项分别影响连接方向、强一致存储和协调机制，不应在实现时隐式承诺。

2026-10-20 用户后续要求保持轻量、暂不引入数据库。验证码改由指定 LyWaf 节点统一管理，任意节点通过签名通信申请签发或消费；递增序号用于顺序校验，独占写入和刷盘后的已消费记录保证单次消费。跨公网/NAT及多 Controller HA 仍属于可选后续范围。
