# 产品定位与能力边界

LyWaf 的目标是基于 ASP.NET Core 与 YARP 提供可自托管的 Web 安全网关，把 HTTP 反向代理、WAF、访问控制、流控、事件、统计和插件管理放进同一套可观察工作流。项目路线不以竞品功能数量为排序依据。

## 横向定位

| 领域 | Nginx | Caddy | Envoy | Traefik | LyWaf 的选择 |
|---|---|---|---|---|---|
| 通用 Web/静态文件 | 成熟且生态广 | 简洁、自动 HTTPS | 非主要定位 | 非主要定位 | 提供常用能力，不复制全部模块 |
| 动态控制面 | 配置与商业生态 | Admin API | 完整 xDS/服务网格 | 多基础设施 Provider | 稳定管理 API、版本化配置和按需 Provider |
| Web 安全工作流 | 模块或外部产品 | 模块或外部服务 | Filter/外部授权 | Middleware/插件 | 内置 WAF、CC、IP 组、验证码、事件与防篡改 |
| 扩展 | C/njs/Lua | Go 模块 | Filter/WASM | Plugin/Provider | 受版本约束的 .NET SDK、签名包和控制台页面 |
| 邮件和旧应用协议 | 有成熟模块 | 可扩展 | 四层/专用 Filter | 四层入口 | 不在 HTTP 安全网关核心内复制 |

## 明确不做

1. 不以替代 Nginx 全部静态文件、缓存、FastCGI、uwsgi、SCGI、邮件和协议模块生态为目标。已有成熟适配器时，LyWaf 可以在其外层承担 TLS/WAF，或只保护 Web/API 入口。
2. 不复制 Envoy 完整 xDS、Service Mesh 和全部 Filter。LyWaf 的配置分发只实现自身节点所需的版本、验证、灰度、原子应用和回滚。
3. 不一次性复制 Traefik 的全部基础设施 Provider。服务发现保持抽象，但新增 Provider 必须有真实部署需求、故障语义和测试环境。
4. 不按功能勾选数量决定优先级。可观测性、故障韧性、数据安全、有界资源和可回滚配置优先于新增协议名称。
5. 没有可复核基准数据时，不宣称性能超过 Nginx、Caddy、Envoy 或 Traefik。所有对照必须遵守 `29-性能基准.md` 的同机、同上游、同协议和同功能规则，并报告错误率与资源占用。

## 能力采用规则

新能力进入核心前必须回答：是否属于 Web 安全入口职责；是否存在真实使用场景；失败时如何降级；内存、队列、连接和文件是否有界；如何监控；如何测试；配置能否回滚。只满足“其他软件有这个功能”不足以进入路线图。

协议转换、邮件网关、完整服务网格或大量基础设施集成应优先通过专用上游、独立进程或插件实现。只有需求规模、维护责任和兼容测试明确后，才重新评估进入核心。
