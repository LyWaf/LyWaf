# POP3、IMAP、SMTP 代理评估

## 当前结论

LyWaf 不把 POP3、IMAP 或 SMTP 应用层代理纳入核心目标。现有 TCP Stream 能做受 ACL、连接数、健康检查和字节速率限制保护的四层透传，但不解析邮件命令、用户身份、邮箱状态或消息正文，因此不能替代专用邮件代理。

完整邮件代理至少需要处理：

- SMTP EHLO/HELO、MAIL/RCPT/DATA、扩展协商、队列状态与退信语义。
- POP3/IMAP 多行响应、literal 长度、命令标签、认证状态和长连接空闲管理。
- STARTTLS 协议内升级、SNI/证书、明文认证禁止和 TLS 降级防护。
- SMTP AUTH、SASL 机制、凭据保护、速率限制、反垃圾与病毒扫描接口。
- 上游错误到客户端协议响应的正确映射，而不是简单断开 TCP。

这些职责与 HTTP WAF 的路由、Header、状态码和正文过滤模型不同，错误实现会直接造成凭据泄漏、邮件丢失或重复投递。

## 可用方案

需要简单高可用时，可使用 LyWaf TCP Stream 在 TLS passthrough 模式下把连接分发给同协议邮件服务器；此时 TLS 与认证完全由上游负责，同一会话固定在选中的上游，禁止 HTTP 重试语义。

需要协议感知代理时使用 Postfix、HAProxy、Nginx Mail、Dovecot proxy 或邮件平台自带入口，并将 LyWaf 保留在 Web 管理端、Webmail 和 HTTP API 前。

## 重新评估条件

只有 LyWaf 的产品定位明确扩展到邮件安全网关，并具备协议专家、互操作测试环境、邮件队列与反滥用需求时才重新评估。届时应作为独立进程或插件产品线设计，不能把协议解析塞进当前 HTTP 中间件管线。
