# 多上游路由、负载均衡与健康检查

> 专栏第 5 篇。目标是从“能转发”走向“节点故障时仍能服务”。

## 多上游

```ly
example.com {
    proxy = [
        "http://10.0.0.11:8080",
        "http://10.0.0.12:8080"
    ]
    lb_policy = RoundRobin
}
```

轮询只负责选择节点，不代表节点健康。没有健康检查时，故障节点仍可能收到请求。

## 负载策略如何选择

- `RoundRobin`：节点能力接近，最容易理解。
- 最少请求/连接：请求耗时差异较大。
- 加权策略：节点规格不同。
- IP Hash/一致性哈希：需要一定会话粘性，但仍应优先把会话外置。
- A/B 策略：灰度和实验流量，不等同于故障转移。

先选简单策略，确认指标后再增加权重和哈希。

## 健康检查

```ly
example.com {
    proxy {
        to = ["http://10.0.0.11:8080", "http://10.0.0.12:8080"]
        lb_policy = "RoundRobin"
        timeout = "00:00:30"
        max_connections = 200
        health_check {
            Active {
                Enabled = true
                Interval = "00:00:10"
                Timeout = "00:00:03"
                Path = "/health"
            }
        }
    }
}
```

健康接口不能只返回“进程还活着”。数据库或关键依赖完全不可用时，它应反映应用无法处理请求；但也不要把非关键依赖波动设计成节点频繁上下线。

## 超时与连接池

超时过短会误杀慢请求，过长会让故障请求占用连接。上传、导出和普通 API 应使用不同路径或上游策略。`max_connections` 既保护上游，也可能成为入口排队点，需要结合上游容量设置。

## 故障演练

1. 连续请求确认流量分布。
2. 停止一个上游。
3. 观察健康状态、错误率和剩余节点流量。
4. 恢复节点，确认它不会在未就绪时过早接流量。
5. 模拟全部上游失败，确认错误页面和告警。

## 完成标准

每个上游都能被单独访问，流量分布符合策略，故障节点会在阈值后摘除并在恢复后重新加入。会话亲和场景还要确认键稳定；全部节点故障时客户端获得明确错误，控制台和日志能够定位 Cluster 与 Destination。

## 生产注意

健康检查路径应验证关键依赖但保持轻量。重试只用于可安全重放的请求，不能用负载均衡掩盖有状态应用设计问题。
