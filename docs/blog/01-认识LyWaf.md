# 认识 LyWaf：为什么把安全网关放在应用前面

> 专栏第 1 篇。本文不急着写配置，先建立 LyWaf 在系统中的位置和职责边界。

## 一个常见的上线问题

应用最初往往直接监听公网端口。业务增长后，我们开始补 HTTPS、黑名单、限速、攻击检测、访问统计和多节点负载均衡。若这些能力散落在每个应用里，不同语言和团队会重复实现，策略也很难保持一致。

LyWaf 的做法是在客户端和业务服务之间放置统一网关：

```text
客户端 -> LyWaf -> 一个或多个业务服务
             |
             +-> 控制台、统计、规则和插件
```

业务服务仍负责身份认证、权限和业务校验；LyWaf 负责入口层能够统一完成的流量治理与安全处理。

## LyWaf 能做什么

- 使用 YARP 完成反向代理、多域名路由和负载均衡。
- 使用自定义规则识别 SQL 注入、XSS、敏感文件和异常请求。
- 提供 IP/CIDR、IP 组、地理位置、连接数和频率控制。
- 管理 TLS 证书、ACME 自动签发和 HTTP 到 HTTPS。
- 使用 DuckDB 保存统计数据，提供 Vue 控制台。
- 通过插件扩展代理中间件、后台任务、页面和 API。
- 通过网页防篡改插件维护已确认响应基线。

## 它不应该替代什么

WAF 不能替代安全编码。参数化 SQL、输出编码、严格鉴权、最小权限和依赖更新仍然必须在应用内完成。CORS 也不是认证，IP 白名单更不能替代账号权限。

正确边界是：入口层过滤明显恶意和异常流量，应用层继续执行完整业务安全检查。

## 一次请求经历什么

请求进入 LyWaf 后，大致经过流量统计、CORS、插件、访问控制、WAF、验证码、CC、限速，再进入文件服务、简单响应或 YARP 上游转发。响应返回时还可能经过压缩、响应头转换和防篡改处理。

顺序很重要。例如 CORS 预检应该在访问上游前结束，网页防篡改需要在响应发送前决定返回上游内容还是安全基线。

## 谁适合使用

- 有多个 Web/API 服务，希望统一入口策略的团队。
- 需要在应用不改代码的前提下增加流量防护。
- 需要自托管网关和可扩展插件，而不是依赖单一云厂商。
- 希望在 Windows 或 Linux 上以 .NET 服务部署。

## 专栏最终会完成什么

我们会从一个监听 8080 的测试应用出发，逐步得到：

```text
公网 HTTPS -> LyWaf
              ├─ 域名/路径路由 -> 多个健康上游
              ├─ WAF、限速、CC、IP 组、CORS
              ├─ 网页防篡改插件
              └─ 控制台、DuckDB、备份和监控
```

## 读者实验

画出自己当前的入口拓扑，标注 DNS、CDN/LB、LyWaf、源站和控制端口，并回答：真实客户端 IP 从哪里来、TLS 在哪里终止、源站能否被绕过、配置和数据备份在哪里。无法回答的部分就是后续部署优先补齐的风险。

## 完成标准

读者能够区分数据面与控制面，理解 WAF 不能替代链路清洗、应用修复和备份，并明确本专栏最终要建立的生产链路。

## 本篇小结

LyWaf 的价值不在于“多加一层代理”，而在于把所有入口请求放进同一套可观察、可配置、可扩展的处理管线。
