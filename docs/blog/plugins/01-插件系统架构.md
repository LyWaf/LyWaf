# 插件系统架构与边界

LyWaf 插件不是单纯的 DLL 扫描器。它同时覆盖服务注册、生命周期、控制端中间件、YARP 代理管线、后台任务、事件通信、统一 API 和前端页面。

## 一次启动的完整链路

1. `AddLyWafPlugins` 绑定 `Plugins` 配置并创建 `PluginManager`。
2. 管理器扫描当前程序集和 `PluginDirectory` 下的 DLL。
3. 所有已发现插件执行 `ConfigureServices`，使运行时启用仍能解析依赖。
4. 已启用插件执行 `InitializeAsync`。
5. 应用构建控制端和代理端中间件管线。
6. `PluginHostedService` 调用 `StartAsync`；关机时逆序调用 `StopAsync`。

## 两条中间件管线

`ConfigureMiddleware` 进入 LyWaf 控制端应用管线，适合控制台侧通用处理。`ConfigureProxyPipeline` 进入实际反向代理管线，适合检查、记录或改写业务流量。不要把 WAF 请求处理写进控制端管线。

代理插件按 `PluginPriority` 排序：`Highest`、`High` 在核心中间件前执行，`Normal`、`Low`、`Lowest` 在核心中间件后执行。安全阻断才应使用高优先级，统计和响应加工通常使用普通或低优先级。

## 内置与外部插件

内置插件编译进主程序集；外部插件从 `plugins/**/*.dll` 加载到独立 `AssemblyLoadContext`。`SystemPlugins` 中的 ID 被视为系统插件，外部 DLL 不能覆盖同名系统插件。

前端页面目前由 Vite 在构建期扫描 `Frontend/src/plugins/*/plugin.ts`。因此外部 DLL 可以独立提供后端能力，但若需要控制台页面，仍需把前端模块编入控制台并重新构建。

## 运行时启停边界

启用和禁用会调用插件的初始化、启动与停止逻辑，但 ASP.NET Core 已构建的中间件管线不会动态重建。只包含服务、任务或 API 的插件可运行时启停；新增或移除中间件、替换 DLL、增加前端页面时应重启 LyWaf。插件中间件还应自行检查启用状态，防止禁用后继续处理请求。

## 核心对象如何协作

| 对象 | 负责内容 | 生命周期 |
|---|---|---|
| `PluginManager` | 发现、排序、启停和状态查询 | 宿主单例 |
| `ILyWafPlugin` | 声明插件能力 | 每个插件一个实例 |
| `IPluginContext` | 提供 DI、配置、日志、目录和事件 | 初始化插件时创建 |
| `IPluginEventBus` | 插件间进程内通知 | 宿主单例 |
| `PluginHostedService` | 将插件启停接入宿主生命周期 | 托管服务 |
| `IPluginApiHandler` | 接收统一控制台 API 分派 | 由插件实例实现 |

插件管理器按优先级再按 ID 排序，因此相同优先级下顺序是稳定的。不过不应依赖字母顺序表达业务依赖；需要前后关系时应选择明确优先级，并在初始化阶段验证依赖插件是否存在。

## 选择插件还是核心功能

适合插件化的功能通常拥有独立配置、数据、页面、后台任务或可关闭的请求处理。路由解析、认证边界、插件统一 API 和宿主启动流程属于核心基础设施，不应由某个业务插件复制。

判断标准如下：

- 功能关闭后不应影响 LyWaf 基本反向代理能力。
- 功能能够使用稳定接口与宿主通信，而不是读取大量核心内部状态。
- 插件异常可以被隔离，数据目录可以独立备份或删除。
- 前端页面能通过统一插件 API 工作，不需要新增核心专用端点。

## 请求路径示意

业务请求进入 YARP 代理分支，先经过高优先级插件、核心安全中间件，再经过普通和低优先级插件。控制台请求进入主应用管线；`/api/plugins/{id}/proxy/*` 在控制端口被分派给目标插件。两类请求不要混为一条管线，否则管理 API 可能被错误地转发给上游。

## 本篇验证

启动时搜索日志中的“共发现 N 个插件”和“启动插件”。控制台插件列表应与 `PluginManager.GetAllPlugins()` 的发现结果一致；禁用插件后应看到停止日志，但涉及代理中间件的行为要在重启后再做最终确认。
