# IpLogMiddleware：指定 IP 深度日志

## 位置

位于 AccessControl 之后、AutoHttps 与 WAF 之前。它只观察已经通过访问准入的指定 IP 请求。

## 是否记录的判断

中间件从 `SharedData.IpLogTargets` 查询客户端 IP。未命中时直接调用下游，开销很小；命中后才进入完整捕获流程。

## 捕获内容

- 时间、请求行、Host、Scheme、客户端 IP。
- 请求 Header。
- 有上限的请求 Body。
- 最终状态码和持续时间。
- 有上限的响应 Body。

组合后的单条日志再次检查 UTF-8 字节数，超过上限会截断，再异步写入文件。

## 响应阶段

它通过 `HttpUtil.CaptureResponseBodyAsync` 包装下游响应。只有下游完成后，才能把状态码、耗时和响应内容组合进同一条记录。

## 为什么不是全量开启

请求/响应 Body 可能包含口令、Token、Cookie、个人信息和大文件。全量长期记录既增加内存和磁盘，也扩大敏感数据暴露面。该功能适合针对特定来源短时诊断。

## 顺序影响

放在 AccessControl 后意味着被黑名单提前拒绝的请求不进入深度 Body 日志，但仍有拦截事件。放在 WAF 前使其能够捕获 WAF 后产生的最终响应。

## 排障与运维

- 无日志：检查 IP 是否是系统识别的真实地址。
- Body 为空：GET 本来无 Body，或捕获上限/流状态不允许。
- 磁盘增长：及时移除监控目标并配置日志保留。
- 安全审计：日志目录只允许运维账号访问。

## 脱敏与保留

记录前应对 Authorization、Cookie、Set-Cookie、密码和 Token 字段脱敏。二进制、压缩和 multipart Body 不适合直接转为文本。诊断任务应设置自动过期，避免忘记关闭后持续收集。

## 验证方法

指定一个测试 IP，发送带 JSON Body 和敏感头的请求，确认大小截断、脱敏、状态码和耗时正确。移除目标后再次请求应不再写日志，并检查日志轮转与目录权限。
