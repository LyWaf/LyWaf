# CaptchaMiddleware：人机验证

## 位置

位于 WafControl 后、CcProtection 前。WAF 或其他策略可把客户端 IP 标记为待验证，后续请求在此被接管。

## 两类请求

### 验证码内部接口

路径前缀为 `/__captcha/`：

- `challenge`：生成 Token、模式、题图或滑块数据。
- `verify`：读取 JSON、行为数据和答案并验证。
- 未知 Action：返回 404。

这些接口由中间件直接处理并短路，不转发上游。

### 普通业务请求

通过真实 IP 查询 `ICaptchaService.IsPending`。没有待验证状态时继续；存在时返回 403 HTML 验证页面，并设置 no-cache。

## 验证流程

验证接口绑定 Token 与客户端 IP，可附带鼠标轨迹、持续时间和滑块偏移等行为数据。成功后服务解除待验证状态，客户端重新请求原业务 URL 才会进入下游。

## 为什么不自动重放原请求

原请求可能带一次性 Body、支付操作或不可重复副作用。验证码成功后由客户端重新发起，比中间件缓存并重放任意业务请求更安全。

## 适用边界

适合浏览器页面，不适合服务间 API、Webhook 和命令行客户端。API 应优先使用明确的 429/403、Token 和速率限制。

## 排障

- 验证后仍反复出现：真实 IP 在前后请求中不一致，或状态未清除。
- 验证 API 404：正确前缀是 `/__captcha/`。
- 页面被缓存：检查外层 CDN 是否忽略 Cache-Control。
- 响应已经开始：中间件不会再覆盖，应检查前置组件过早写 Body。

## 状态安全

Challenge Token 应短时有效、一次性使用并绑定客户端特征。验证接口需要请求体大小限制和频率限制，不能让验证码本身成为计算型攻击入口。多实例部署时状态需要共享或保持会话粘连。

## 验证方法

测试正确答案、错误答案、过期 Token、重复提交、不同 IP 重放和高频获取 Challenge。浏览器验证成功后应回到原页面；API 路由应配置为不触发交互式验证码。
