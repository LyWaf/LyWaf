# BasePluginMiddleware：插件事件总线入口

## 位置

由 `UseLyWafPlugins()` 注册在全局管线。插件自定义全局中间件先注册，随后才是 BasePluginMiddleware。

## 主要职责

1. 跳过控制台监听端口，避免插件请求事件污染管理 API。
2. 获取真实客户端 IP。
3. 判断 HTTP 还是 WebSocket。
4. 更新 `ConnectionTracker` 活跃连接数。
5. 发布 `RequestStartedEvent`。
6. 调用下游。
7. 在 `finally` 中释放连接跟踪并发布 `RequestCompletedEvent`。

## 短路条件

它本身不拦截业务请求。控制台端口会跳过事件发布，但仍调用下游。只有事件订阅者异常未被隔离时，才可能间接影响请求，这也是插件事件处理必须捕获异常的原因。

## 响应阶段

普通 HTTP 在响应完成后发布结束事件；WebSocket 则通常在连接关闭后发布。结束事件包含最终状态码、访问时间和完整持续时间。

## 为什么使用 finally

无论下游正常、短路还是抛异常，连接计数都必须释放。如果只在正常返回后释放，异常流量会让活跃连接永久偏高。

## 性能与安全

事件订阅者位于请求关键路径。耗时 I/O 应进入有界后台队列，不能同步写远程服务。事件中包含 HttpContext，订阅者不要在请求结束后无界持有它。

## 排障

- 插件没有请求事件：检查请求是否走控制台端口、插件是否运行、订阅是否成功。
- WebSocket 耗时异常长：这是连接存续时间，不是单次握手时间。
- 活跃连接不归零：检查异常路径和订阅者是否阻塞结束事件。

## 事件消费约束

事件总线按订阅处理器逐个等待。处理器应只读取必要字段并投递到有界队列，不能在请求结束后保存整个 `HttpContext`。需要长期保存的数据应复制为不可变 DTO，并删除 Authorization、Cookie 等敏感头。

## 验证方法

分别制造正常响应、下游短路、异常和 WebSocket 关闭，确认 Started/Completed 成对出现且连接计数归零。再加入一个故意失败的订阅者，确认错误被记录但其他订阅者仍执行。
