# 深入 LyWaf 中间件：一次请求如何穿过完整防护链

> 专栏第 6 篇。本文按照 `Program.cs` 的真实注册顺序，逐个解释全局和代理中间件，并说明它们何时继续、何时短路请求。

本文用于建立全局视角。需要逐个组件独立发布或深入阅读时，进入 [LyWaf 中间件逐篇解析](middleware/README.md)，其中每个中间件都有单独文章。

## 先理解执行方向

ASP.NET Core 中间件不是简单的从上到下列表。请求按注册顺序向内执行，响应在 `await next()` 返回后按相反顺序向外执行：

```text
请求  -> A -> B -> C -> 上游
响应  <- A <- B <- C <- 上游
```

中间件可以：

1. 在调用下游前检查或修改请求。
2. 不调用 `next`，直接返回响应，这叫短路。
3. 在下游完成后检查或修改响应。
4. 用流包装 `Request.Body` 或 `Response.Body`，观察传输数据。

LyWaf 的顺序不是装饰。访问拒绝必须发生在上游之前，错误响应统计只能在下游完成后读取状态码，带宽统计则要包住整个代理管线。

## 管线全貌

```text
全局：WebSocket -> 全局插件 -> ACME Challenge

代理：BandwidthCounting
   -> Cors
   -> ResponseCompress
   -> 高优先级插件（含 WebTamper）
   -> AccessControl
   -> IpLog
   -> AutoHttps
   -> WafControl
   -> Captcha
   -> CcProtection
   -> Throttled
   -> SpeedLimit
   -> CcResponseMonitor
   -> 普通/低优先级插件
   -> SimpleRes
   -> FileProvider
   -> LoadBalancing
   -> YARP 转发
```

控制台 API 通过单独端点处理，反向代理仅匹配业务监听端口，因此控制台请求不会误入业务代理链。

## 全局阶段

### 1. WebSocket 支持

`UseWebSockets` 让后续代码能够识别升级请求并使用 WebSocket API。它不是业务代理本身，但必须在需要读取 `context.WebSockets` 的组件之前启用。

排障重点：普通 HTTP 正常而 WebSocket 失败时，检查 Upgrade/Connection 头、外层代理支持和上游协议，而不是先调整 WAF 规则。

### 2. 全局插件与 BasePluginMiddleware

`UseLyWafPlugins` 先注册插件的全局中间件，再加入 `BasePluginMiddleware`。基础中间件向事件总线发布请求开始和完成事件，让不直接进入代理管线的插件能力也能观察生命周期。

插件异常必须自行隔离；全局插件影响范围可能包括控制台和非代理端点，使用时比代理插件更谨慎。

### 3. AcmeChallengeMiddleware

它匹配 `/.well-known/acme-challenge/`。找到 Token 时直接返回 200，Token 不存在时返回 404，均不会进入代理；其他路径继续。

它位于自动 HTTPS 之前，因为 HTTP-01 CA 必须通过 HTTP 获取 Challenge。顺序反过来可能让证书首次签发和续期失败。

## 代理阶段

### 4. BandwidthCountingMiddleware

这是代理管线最外层。它用 `CountingStream` 包装响应流，最终统计实际写出字节，并估算请求/响应头与请求体大小，写入共享带宽统计。

它使用 `finally` 恢复原始响应流，因此即使下游抛异常也会完成清理。放到内层会漏掉被安全中间件提前拒绝的流量。

排障重点：这里的 Header 大小是估算值；响应 Body 是实际写入值。压缩位于内层，因此出站统计更接近最终压缩后传输量。

### 5. CorsMiddleware

CORS 配置在 `config.ly` 转换为 YARP 路由元数据 `_Cors`。中间件读取当前 RouteModel，检查请求 Origin：

- 路由没有 Cors 或 Origin 不允许：直接继续，不主动授予跨域权限。
- 合法普通请求：注册 `OnStarting`，在响应发送前写入跨域头。
- 合法预检 OPTIONS：直接返回 204，不访问上游。

它放在安全链前，是为了让浏览器预检不被业务认证、验证码或上游处理阻塞。CORS 通过不代表业务请求自动通过，后续认证和 WAF 仍然执行。

### 6. ResponseCompressMiddleware

它根据 `Accept-Encoding` 选择 Brotli 或 Gzip，并检查 HTTPS 开关、最小响应大小、MIME、状态码和已有 Content-Encoding。只有压缩后确实更小时才使用压缩结果，同时写入 `Vary: Accept-Encoding`。

当前实现会先把响应缓冲到 `MemoryStream` 再决定是否压缩，因此超大动态响应需要特别关注内存。大文件下载可关闭对应 MIME 压缩、提高阈值或使用预压缩静态文件。

它位于防篡改插件外层。响应回程时，防篡改先选择安全基线或当前内容，然后压缩最终要发给客户端的内容。

### 7. 高优先级插件阶段

`Highest` 和 `High` 插件在核心安全中间件之前注册。适合必须早期捕获或保护响应的系统插件，不代表所有插件都应该选择高优先级。

#### WebTamperMiddleware

网页防篡改属于高优先级插件，但它调用下游取得完整响应后才做判断：

1. 内部检查请求通过专用 Header 标识，移除标识后跳过自身，避免递归。
2. 插件未运行或资源未受保护时直接继续。
3. 命中资源时移除 `Accept-Encoding`，让上游返回可比较的原始内容。
4. 响应流入受限临时文件，而不是全部放进内存。
5. 只处理成功且未超大小限制的响应。
6. 计算文件 Hash、记录实际路径并惰性加入后台检查队列。
7. Hash 变化时改为流式返回安全基线，并移除旧 ETag/Last-Modified。
8. 最终恢复 Header、响应流，关闭句柄并删除临时文件。

它必须包住后续上游响应；如果放在 YARP 之后，就没有机会替换已经发送的内容。

### 8. AccessControlMiddleware

访问控制先获取真实客户端 IP 和路径，再按以下顺序执行：

1. IP、路径 IP 和地理位置检查。
2. 被拒绝时记录拦截事件，使用统一错误模板返回并短路。
3. 开启连接限制时，按 IP、目标 Cluster 和路径尝试获取连接额度。
4. 获取失败返回配置的拒绝状态。
5. 获取成功后进入下游，并在 `finally` 中释放连接额度。

连接释放使用 `finally` 很关键，否则异常请求会永久占用计数。真实 IP 配置错误会让黑白名单、地理判断和连接限制同时失真。

### 9. IpLogMiddleware

它不是记录所有请求，而是检查客户端 IP 是否位于动态监控目标列表。命中时捕获请求行、Header、受限请求体、响应状态、耗时和受限响应体，异步写入 IP 专项日志；未命中几乎直接继续。

它放在访问控制之后，因此只记录通过访问控制的完整请求。Body 和 Header 可能包含密码、Token 和隐私数据，监控目标应临时启用，日志文件必须限制权限并设置保留周期。

### 10. AutoHttpsMiddleware

它根据实际本地 HTTP 监听端口查找 `AutoHttpsPort`。命中后构造同 Host、Path 和 Query 的 HTTPS URL，返回永久重定向并短路；没有映射则继续。

ACME Challenge 已在全局阶段提前处理，不会被重定向。外层代理终止 TLS 时要正确传递协议，否则可能出现重定向循环。

### 11. WafControlMiddleware

这是请求内容检测核心，承担的工作比名称更广：

- 按域名和路径决定日志采集。
- 在需要时安装请求/响应捕获流。
- 应用请求体大小限制。
- 检查快速拒绝原因和白名单路径。
- 检查 Query 参数和 POST Body 攻击特征。
- 调用自定义与系统 WAF 规则。
- `Observe` 仅记录并继续，其他动作执行后短路。
- 捕获格式错误和超大 Body，返回 400/413。

它位于 AutoHttps 后，避免对本应重定向的 HTTP 内容做完整攻击分析；也位于 Captcha 和 CC 前，让明确攻击先进入 WAF 事件链。

### 12. CaptchaMiddleware

验证码中间件有两类请求：

- `/api/captcha/*`：创建、刷新和验证 Challenge，由中间件直接处理。
- 普通请求：IP 没有待验证状态时继续；存在待验证状态时返回验证码页面并短路。

验证成功后解除待验证状态，后续原业务请求才能继续。它适合浏览器，不适合纯 API 客户端。响应已经开始时不再尝试覆盖，避免产生损坏响应。

### 13. CcProtectionMiddleware

它按真实 IP 调用 CC 规则检查器，识别高频访问、高频攻击等请求侧条件：

- 未触发：继续。
- `LogOnly`：执行记录动作后继续。
- Block、Captcha、Reject、RateLimit 等动作：执行后短路。

和普通限速相比，CC 依赖统计窗口与复合行为。它放在 WAF 后，可以利用之前产生的攻击事件。

### 14. ThrottledMiddleware

这里的 Throttled 是带宽节流，不是请求次数限制。它按优先级选择路径、IP 或全局 KB/s 限制，用包装流控制响应写出速度：

```text
PathLimits -> IpLimits -> Global
```

路径流按目标时间分块写入；IP 流从共享 Token 中申请带宽。完成后在 `finally` 恢复原始 Body，包装流不负责关闭 ASP.NET 的底层流。

同步 `Write` 目前直接写到底层流，主要节流路径依赖异步写入，因此自定义中间件应优先使用异步 Response Body API。

### 15. SpeedLimitMiddleware

SpeedLimit 是请求速率限制。它读取当前 YARP 路由 Metadata 中的 `RateLimiter` 策略，向对应限流器申请 Lease：

- 没有路由策略或找不到限流器：继续。
- Lease 成功：继续。
- Lease 失败：返回配置的拒绝状态并短路。

它和 Throttled 的差异是：SpeedLimit 决定“请求能不能进入”，Throttled 决定“响应每秒写多少字节”。

### 16. CcResponseMonitorMiddleware

它先调用下游，响应返回后读取最终 StatusCode。状态码大于等于 400 时，按客户端 IP 记录错误事件，为 `FrequentError` 类型 CC 规则提供数据。

如果把它放在请求侧提前检查，就看不到上游、文件服务和插件最终产生的错误码。它只记录，不改写本次响应。

### 17. 普通与低优先级插件阶段

`Normal`、`Low`、`Lowest` 插件位于核心安全链之后，适合统计、审计和普通响应改写。此处接收的请求已经通过访问控制和 WAF，但仍可能由后面的 SimpleRes、FileProvider 或 YARP 生成响应。

插件作者应明确需要观察的是原始请求、通过安全检查的请求，还是最终响应，再选择阶段。

### 18. SimpleResMiddleware

它读取 RouteModel.RouteId，仅处理 `simpleres_` 开头的路由。命中配置后设置状态码、Content-Type、额外 Header，替换 Body 中的 Host、Path、Method、ClientIp、Time 等占位符，然后写入响应并短路。

未命中 SimpleRes 路由则继续。它适合健康检查、Mock 和维护响应，不需要建立虚假上游服务。

### 19. FileProviderMiddleware

它只处理 `fileserver_` 路由，并负责：

- 根据 Prefix 和根目录解析真实文件，防止路径错误。
- 目录缺少尾斜杠时重定向。
- 根据 Browse 开关返回目录列表或 403。
- 处理默认首页、TryFiles 和预压缩文件。
- 处理 ETag、If-Modified-Since 与 304。
- 处理 Range、206 Partial Content 和文件流响应。

不是文件路由时继续进入 YARP。目录浏览会暴露文件结构，生产默认关闭；根目录必须最小化，不能指向程序或数据目录。

### 20. LoadBalancing 与 YARP 转发

`UseLoadBalancing` 是自定义代理管线中必须显式加入的 YARP 阶段。它根据 Cluster、健康状态和策略选择 Destination，随后由 YARP 建立上游请求并应用请求/响应 Transform。

它不是普通自定义 Middleware 文件，但属于请求到达上游前的最后关键阶段。缺失时即使路由和集群配置正确，也无法正常选择后端。

## 还有一个不是中间件的路由组件

`PortMatcherPolicy` 是 ASP.NET Core `MatcherPolicy`，在进入代理管线前参与 Endpoint 选择。它处理 Host 中的端口、通配域名和 localhost 等匹配，避免多监听端口产生 AmbiguousMatchException。

因此“请求完全没有进入任何代理中间件”时，应先检查端点和端口匹配，而不是在 WAF 中寻找原因。

## 如何判断请求在哪里被短路

按顺序排查：

1. 是否命中业务监听端口和 YARP Endpoint。
2. OPTIONS 是否被 CORS 返回 204。
3. HTTP 是否被 AutoHttps 返回重定向。
4. AccessControl、WAF、Captcha、CC、SpeedLimit 是否产生拦截事件。
5. RouteId 是否由 SimpleRes/FileProvider 短路。
6. 是否真正进入 LoadBalancing 和上游。
7. 响应回程是否被 WebTamper 替换或 ResponseCompress 压缩。

为请求贯穿统一 Request ID，并在入口、拦截事件和上游日志中关联，是定位管线问题最有效的方法。

## 实验：寻找短路点

准备正常请求、错误 Origin、黑名单 IP、WAF 命中、限流和静态文件六组请求。为它们关联 Request ID，对照入口、拦截事件和上游日志，确认哪一层停止调用 `next`。再测试响应回程的压缩与防篡改，理解请求顺序和响应顺序相反。

## 修改管线的门槛

调整顺序前必须说明需要看到的请求/响应范围，并回归 HTTPS、CORS、WAF、文件、WebSocket、插件和上游故障。不能因为单一场景通过就交换全局组件顺序。

## 本篇小结

LyWaf 的每个中间件只承担一类职责，顺序决定它能看到的数据和能否短路。理解完整链路后，下一篇配置 WAF、CC 和限速时，就能准确判断规则发生在哪个阶段。
