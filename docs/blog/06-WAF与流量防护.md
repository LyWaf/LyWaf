# 从观察到阻断：循序启用 WAF、CC 与限速

> 专栏第 7 篇。目标是建立低误报的上线方法，而不是追求规则数量。

## 为什么先观察

不同业务会合法地传输 SQL 片段、HTML、脚本或长参数。直接启用强阻断，安全规则很可能先影响正常用户。新规则应经历“观察、分析、收窄、阻断”四步。

## 第一条观察规则

```ly
Protect {
    WafRules {
        observe_sensitive_file {
            Enabled = true
            GroupOperator = "Or"
            ConditionGroups = [
                { Operator = "And"; Conditions = [
                    { Field = "UriPath"; Operator = "Regex"; Value = "(?i)/(\\.env|\\.git|config\\.json)$" },
                ]},
            ]
            Action = "Observe"
        }
    }
}
```

观察一个完整业务周期后，如果命中均为攻击探测，再改为：

```ly
Action = "Reject"
ResponseCode = 403
```

## 动作层级

- `Observe`：记录，不影响请求。
- `Reject`：拒绝当前请求。
- `RateLimit`：降低频率，适合高成本接口。
- `Captcha`：适合浏览器可交互页面。
- `Block`：临时封禁来源，干预最强。

API 客户端无法可靠处理验证码，API 路径通常使用明确状态码或限速。

## CC 与普通限速的区别

限速针对已知阈值，例如“单 IP 每分钟最多 60 次登录”。CC 防护基于统计窗口识别高频访问、高频攻击或高频错误，可在异常行为出现后执行不同动作。

静态资源、公开 API、登录、搜索和导出接口的成本不同，不应共用一个全局阈值。

## 真实 IP 是前提

如果 LyWaf 前还有 CDN 或负载均衡器，必须先正确建立可信转发链。否则所有用户可能被识别为同一个代理 IP，或攻击者伪造 `X-Forwarded-For` 绕过限制。

## 调优记录

每次规则变更至少记录：规则 ID、作用域、阈值、负责人、变更原因、观察数据和回滚方式。白名单和排除项还应有失效时间。

## 验证

- 合法业务请求不应被拦截。
- 构造命中请求，检查状态码、事件和日志一致。
- 达到限速阈值后响应明确，恢复时间符合配置。
- 多用户共享 NAT 时不会被过低阈值集体误伤。

## 观察期记录

为每条规则记录域名、路径、字段、动作、启用时间、正常命中样本、攻击样本和回滚人。观察期至少覆盖一个完整业务周期和峰值流量；从 LogOnly 切换阻断后继续观察错误率和客服反馈。

## 应急回退

若出现误伤，优先将具体规则退回 Observe 或缩小范围，不关闭全部 WAF。临时白名单和阈值必须带过期时间，事件结束后清理。

## 本篇小结

WAF 负责请求内容和异常行为，下一篇进一步使用 IP 组和访问控制限制“谁可以访问哪些入口”。
