# 安全防护配置

## 分层思路

安全策略应从低误报到高干预逐步启用：观察日志、拒绝单次请求、限速、验证码、临时封禁。不要在不了解业务流量时一次性开启全部阻断规则。

## WAF 规则

### 请求规范化边界

Args 和 Post 检测共用一次请求检查快照。查询参数、JSON/Form 请求体中的字段名和值会生成受限候选，候选可递归执行 URL、HTML Entity、Base64 和 Hex 解码，以降低多层编码绕过风险。原始值也会保留供规则匹配，解码失败不会中断业务请求。

`Protect.InspectionMaxBodyBytes` 控制 WAF 最多缓冲多少请求体，默认 1 MiB；它不同于接收层的 `MaxRequestBodySize`。超过检查上限的内容会标记为截断，不能据此宣称整个请求已经检查。`InspectionMaxValueLength`、`InspectionMaxCandidates` 和 `InspectionDecodeDepth` 分别限制单值长度、候选总数和递归深度，生产环境不应为了追求检出率无限调大这些值。

规范化管线支持有界 Gzip、Deflate、Brotli 解压，以及 JSON、XML、Form 和 Multipart 结构化取值。XML 禁止 DTD 和外部实体解析；Multipart 只检查已受总请求检查上限约束的内容。解压后超过上限、压缩流损坏、TE/CL 冲突和冲突 Content-Length 会作为协议异常处理。上传接口仍应独立限制请求大小、文件类型和上游处理时间。

### 分类检测

`SemanticDetectionEnabled` 开启可解释的分类检测，覆盖 SQL/命令/代码注入、SSRF、XXE、路径穿越、文件包含、Java/PHP/.NET 反序列化、NoSQL、LDAP、XPath 和模板表达式载荷。检测结果包含稳定规则 ID、攻击类别、输入来源和最多 160 字符的证据摘要。默认 `SemanticDetectionAction = "Observe"`，应先根据真实业务误报校准，再改为 `Reject`。

分类检测使用规范化后的结构值和有超时的上下文签名，并不等于完整 SQL Parser 或语言 AST。固定回归语料位于 `tests/fixtures/security-corpus-v1.json`，载荷采用 Base64 封装以避免端点防病毒软件隔离。测试会输出检出率、误报率、P50/P95 和线程分配量并执行门禁；该合成小样本仅用于防止代码回退，不能作为与其他 WAF 产品的公开效果排名。

`Protect.WafRules` 支持 URI、完整 URL、查询串、Method、客户端 IP、请求头、Cookie、Body 等字段，操作符包括相等、包含、前后缀、正则、存在性和长度比较。

```ly
Protect {
    WafRules {
        block_sensitive_file {
            Enabled = true
            Field = "UriPath"
            Operator = "Regex"
            Value = "(?i)/(\\.env|\\.git|config\\.json)$"
            Action = "Reject"
            StatusCode = 403
        }
    }
}
```

新规则先使用 `Observe`。确认日志中没有合法业务命中后，再切换为 `Reject`、`Block` 或 `Captcha`。

## CC 防护

CC 规则基于统计窗口识别高频访问、高频攻击和高频错误，可执行封禁、验证码、拒绝、限速或仅记录。规则阈值应按接口成本区分：登录、搜索、导出接口通常比静态资源更严格。

## 速率限制

`SpeedLimit` 适合可预测的频率控制。按 IP 限制时要确认真实 IP 获取正确；在 NAT、企业出口或 CDN 后，过低阈值会误伤共享出口用户。

## IP 与地理控制

访问控制顺序上，可信白名单通常用于跳过后续地理检查。管理接口应使用明确的允许列表，而不是依赖“非公开路径”。详细操作见 [IP 组与访问控制](18-IP组与访问控制.md)。

## 验证码

验证码用于介于正常和明确攻击之间的流量。API 客户端通常无法完成人机验证，因此 API 路径应优先限速或返回明确状态码，浏览器页面再考虑验证码。

## HTTPS 与安全响应头

- 使用 TLS 1.2/1.3 和有效证书。
- 确认 HTTP 到 HTTPS 的重定向不会影响 ACME Challenge。
- 按业务兼容性配置 HSTS、CSP、`nosniff` 和 Referrer-Policy。
- CORS 是浏览器访问授权机制，不是服务端身份认证。

## 防篡改

网页防篡改解决的是“已确认内容被替换”问题，不替代 WAF 输入检测。启用后即使上游内容变化，访客仍获得安全基线，管理员通过差异视图确认后更新。详见 [网页防篡改插件](19-网页防篡改插件.md)。

## 调优流程

1. 收集至少一个完整业务周期的正常流量。
2. 按域名、路径、Method 和客户端类型分组。
3. 找出高成本接口并单独设阈值。
4. 先观察命中，再启用干预。
5. 为误报准备临时排除和快速回滚。
6. 定期复核长期白名单、排除项和已停用规则。

## 规则优先级与样本

先处理来源准入，再做内容检测和行为判断。白名单只跳过明确检查，不应成为所有安全层的无限通行证。为每条阻断策略保存正常和命中样本，覆盖编码、重复参数、JSON、表单、大 Body、IPv6 和可信代理。

## 应急处理

大面积误报时先将相关规则切换为 Observe 或缩小域名、路径范围，保留事件证据，不要关闭整个 WAF。攻击期间的临时阈值必须设置恢复时间和负责人，事后回到基线配置并复盘。
# 请求检测后台管理

`GET /api/request-security` 读取请求正文/候选值/解码深度限制、协议异常动作和语义检测状态。`PUT /api/request-security` 更新这些字段；后台只合并 `Protect` 下对应字段，不会覆盖已有 WAF 规则或传统参数规则。
