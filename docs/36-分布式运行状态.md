# 分布式运行状态

## 解决的问题

配置分发只能保证节点拥有相同规则，不能保证运行中的临时状态一致。典型问题包括：节点 A 封禁 IP 后，请求切换到节点 B；验证码在节点 A 生成，却提交到节点 B；同一个插件任务因重试在多个节点重复执行。

LyWaf 的普通运行状态变更采用本地应用、有界异步持久化与复制、周期性反熵。普通复制热路径不等待远程节点；这不代表所有操作都不等待磁盘或网络：持久同步 ACK、快照安装、解封代际落盘及远程验证码签发有各自的等待与失败边界。`RuntimeState.Enabled = false` 时仍保留本地状态和持久化能力，单机不依赖 Redis、数据库或消息系统。

## 状态语义

| 状态 | 域 | 合并方式 | 说明 |
| --- | --- | --- | --- |
| 动态白名单/黑名单 | `access.*` | LWW + 删除墓碑 | 每个 IP/CIDR 独立成键，避免整表覆盖 |
| 临时 IP 封禁 | `ip.blocked` | LWW + TTL | WAF 判定会读取本地缓存或复制状态 |
| 验证码待处理与挑战 | `captcha.*` | LWW + TTL | 本机原子消费不等于跨节点全局单次消费；复制需显式域授权 |
| CC 时间窗口 | `cc.access/attack/error` | G-Counter 分量合并 | 每节点、每次启动Epoch的分量取最大值，再求全局总数 |
| CC 决策与处罚投影 | `cc.decision` / `cc.triggered` | 逻辑决策 + 本地有效性检查 | 按当前规则修订、作用域、代际与覆盖状态执行；收到状态不等于各节点已执行 |
| CC 解封代际 | `cc.policy-generation` | 授权签名 + 持久代际栅栏 | 旧代际处罚不能重新生效；传输 HMAC 权限不等于解封签发权限 |
| 防篡改事件 | `web-tamper.event` | 每资源 LWW | 检测、自动恢复和接受基线都会同步 |
| 插件任务 | `plugin.task` | LWW + TTL | 记录 running/succeeded/failed |
| 插件幂等键 | `plugin.idempotency` | 本地原子占用 + 复制 | 正常网络下抑制重复执行 |

普通 LWW 版本由 `(Sequence, NodeId)` 确定，序列相同时按节点 ID 稳定裁决。删除保留 24 小时墓碑；不能据此承诺任意长离线后旧值不会复活。压缩保留的过期版本栅栏受硬预算约束，DurableSync 另有离线窗口、快照替换与旧 epoch 拒绝机制。它们不能由普通 merge 的定时重发代替。

## 配置

```ly
RuntimeState {
    Enabled = true
    NodeId = "edge-01"
    StateDirectory = ".lywaf-runtime-state"
    QueueCapacity = 10000
    MaxValueBytes = 65536
    MaxJournalBytes = 134217728
    AllowedClockSkewSeconds = 60
    SharedSecret = "${RUNTIME_STATE_SECRET}"

    Peers {
        edge-02 {
            Endpoint = "https://10.0.0.12:7030"
            ProtocolVersion = 1
            Send {
                AllowedDomains = ["ip.blocked"]
                AllowUngroupedKeys = true
            }
            Receive {
                AllowedDomains = ["ip.blocked"]
                AllowUngroupedKeys = true
            }
        }
    }
}
```

每个节点的 `NodeId` 必须唯一且重启后保持不变。生产节点间接口应使用 HTTPS；共享密钥通过环境变量注入，不要提交到仓库。若使用节点独立密钥，发送端目标配置和接收端发送节点配置必须使用同一密钥。

接收端必须在 `Peers` 中显式登记并启用发送节点；知道共享密钥但未登记或已禁用的节点也会被拒绝。升级前检查双向Peer配置，不能仅配置发送方向。

上述示例只授权两个节点复制无保护组的 `ip.blocked`，不是所有运行域的通配授权。edge-02 使用相同配置，但将 `NodeId` 改为 `edge-02`、Peer 名改为 `edge-01`、Endpoint 改为 `https://10.0.0.11:7030`，StateDirectory 使用该节点自己的目录；两端设置相同的 `RUNTIME_STATE_SECRET`，并使用可验证的 HTTPS 证书。生产启动注册的 `AddLyWafRuntimeState` / `MapLyWafRuntimeStateApi` 使用这里的 RuntimeState 配置，默认 v1 接口为 `/api/runtime-state/agent/merge`。如果同时启用了 NodeCommunication，必须允许旧协议且不能存在禁止 `runtime.merge` 的已登记 Peer，否则 v1 会被拒绝。

`Send` 和 `Receive` 都是默认拒绝：只有 Endpoint/Secret 不足以复制。需要带保护组的键时，应配置 `ProtectionGroupKeyPrefixes` 与双方策略的 `AllowedProtectionGroups`；不能靠 `AllowUngroupedKeys` 绕过已有保护组绑定。此双节点示例不授予 `TrustedForwardedSources`：加入第三节点并通过另一节点反熵转发时，还需按实际拓扑显式授权被转发的来源。切换 v2 时还必须配置 NodeCommunication 的集群身份、双方密钥及 operation 权限，不能只改 ProtocolVersion。

## 数据与内存边界

### 短窗口的持久存储要求

节点认证必须先持久占用 nonce 才处理请求。`NodeCommunication.StateDirectory` 的扫描与强制落盘延迟会影响 CC 覆盖证据更新，不能通过关闭 fsync、清空防重放目录或放宽证据有效期来规避。部署时将协议和运行状态目录放在受保护、容量足够的本地持久存储，并实测峰值负载下的延迟；不要把临时 RAM 存储当作性能优化。

2026-10-20 同一冻结二进制的三进程对照中，D 盘的一秒/单主体实验未建立完整水位；改用 C 盘持久目录后完整通过，无新业务请求时决定约 166ms，独立持久收据约 1038ms。完整哈希、硬件观察及失败记录见 [CC 进程验证](cc-e3-process-fault-verification.md)。这不是所有 SSD、节点数或攻击规模的延迟承诺，也不能推广为严格全局限流。短窗证据过期时必须如实显示 Partial；要求完整覆盖的规则可能暂不产生新决定，不能把缺失节点计数当零或用旧窗口补发处罚。已合法生效且尚未到期的决定仍按其作用域、修订号和解封代次执行。

普通状态使用受预算约束的本地存储及有界后台日志队列，追加到 `runtime-state.jsonl`；普通合并成功不是磁盘 fsync 证明。日志恢复逐行读取。DurableSync 的接收 ACK 必须等待日志与检查点持久化栅栏，快照安装及 CC 解封代际也有独立的持久提交路径。

- `MaxValueBytes` 限制单条正文，默认 64 KiB。
- `MaxJournalBytes` 是日志压缩触发阈值，默认 128 MiB，不是磁盘硬上限。
- `MaxStateEntries` / `MaxStateBytes`、`MaxJournalQueueBytes`、`MaxJournalDiskBytes` 以及 `MaxDiskBytes` / `MaxDiskFiles` 分别约束状态、日志队列和磁盘；容量拒绝不能伪造持久 ACK。
- `QueueCapacity` 约束队列条目，复制还受共享及单队列字节预算约束。普通异步路径可能丢弃入队，持久同步不能把这种入队当作已确认交付。
- API 状态摘要不返回正文，避免泄露验证码答案、封禁原因或插件数据。

日志追加与原子替换压缩均已实现，压缩保留存活状态、必要的过期版本和同步检查点。超出保留栅栏或暂存预算时安全拒绝，不通过删除旧证据腾空间。应监控持久化/丢弃计数、容量错误和目录占用；`PersistedMutations` 本身不是 fsync ACK。配置语义及验收边界见 [存储容量专项](runtime-state-capacity.md) 与 [最终验收说明](node-communication-final-verification-2026-10-20.md)。

## 复制协议

复制使用独立 Peer 队列与发送任务，隔离慢节点的在途发送；入口、Peer 队列、暂存和在途批次共享 `ReplicationQueueMaxEntries` / `ReplicationQueueMaxBytes`，另受 `QueueCapacity` 与 `ReplicationQueuePerQueueMaxBytes` 限制。共享预算耗尽仍会影响新变化准入，不能承诺慢节点完全不影响系统。丢弃后尝试通过反熵补偿，不保证恢复时限或每条变化都送达。详见 [复制队列预算与优先级](runtime-state-replication-queue.md)。

`GET /api/v1/runtime-state/status` 的 `replication.droppedMutations` 返回本进程复制队列丢弃次数（与持久化丢弃数分开），每个目标队列的一次丢弃分别计数。该指标不代表丢失的唯一状态键数，也不等于已完成补偿的数量。关闭服务时取消各节点在途请求；复制请求禁止自动跳转到其他地址。

本地变更尝试进入复制队列。v1 向 `/api/runtime-state/agent/merge` 逐条发送；v2 普通模式向 `/api/v2/node-agent/runtime.merge` 批量发送；显式启用 `DurableSyncEnabled` 的 v2 Peer 使用 `/api/v2/node-agent/runtime.sync`。普通远端合并不再次触发即时广播，周期扫描仍可在授权范围内转发。

反熵启动即扫描一页，此后每 30 秒推进一页，页大小为 `QueueCapacity / 2` 限定在 1..256。这是本地状态的游标扫描，不是每 30 秒全量广播；队列拥塞、授权拒绝、网络故障及遍历期间变化都可能延后补偿。没有逐 Peer 确认扫描游标，不能推导“30 秒必然收敛”。

机器接口使用 HMAC-SHA256，签名覆盖操作名、发送节点、时间戳、nonce 和请求体 SHA-256。接收端限制时钟偏差并拒绝 nonce 重放。该接口免 JWT，但仅此 agent 路径免除；以下诊断接口仍要求控制台认证：

- `GET /api/v1/runtime-state/status`
- `GET /api/v1/runtime-state/snapshots?domain=cc.triggered`

## 一致性和故障边界

v1认证nonce写入 `StateDirectory/replay`，与配置分发共用持久防重放组件，重启后继续生效。有效记录上限10000，保留601秒，存储不可用时拒绝复制，不降级为无防重放验证。已有真实 HTTP 容量回归及有限 20 节点实验，但它们不是持续高吞吐、认证吞吐峰值或生产容量定标。

运行状态Peer可设置 `ProtocolVersion = 2`，发送到 `/api/v2/node-agent/runtime.merge`。必须启用NodeCommunication，且其NodeId与RuntimeState.NodeId一致；发送方按目标Peer的ActiveKeyId签名，接收方需为发送者授权 `runtime.merge`，且RuntimeState.Enabled必须为true。v2绑定集群及双方身份，使用NodeCommunication的replay-v2目录。消息可携带其他节点的已合并分量以支持反熵转发，不能把mutation.NodeId简单视为本次发送者。`NodeCommunication.AllowLegacyProtocol = false` 同时禁止运行状态v1发送和接收。v2批量传输与有游标分页修复的具体上限、频率和丢弃语义见下文；分页扫描并非已确认的无损日志订阅。

计数分量字典同样受MaxValueBytes限制：接收单条分量以及与本地分量合并后的字典都必须在限额内，分量键最多512字符，总数不得超过Int64上限。超限拒绝不会覆盖已有计数。该单值限制不是全进程内存上限；当前另有状态条目/字节及队列预算，但序列化、运行时对象和其他服务仍占内存，不能把预算之和当作进程 RSS 上限。

窗口计数分量使用JSON编码的 `[NodeId, Epoch]` 标识，Epoch在每次创建运行状态存储时生成。恢复日志中的旧分量保持原值，后续请求只增加新Epoch分量；即使本机日志丢失，远端保存的旧Epoch也不会覆盖重启后新增的计数。旧版本仅以NodeId命名的分量仍可参与合并，不会被转换或重复累加。窗口到期后全部分量一起清理。此机制无法恢复所有节点都未持久化、也未同步的请求，也不允许将同一NodeId同时分配给多个活动节点；它不是严格一致限流。这里的计数分量 Epoch 与 DurableSync 按方向流持久化并在 bootstrap 中更换的传输 epoch 是不同标识。

高级 CC 已支持 SiteGroup（ProtectionGroup 或 route/host）、Node、Cluster 作用域及解封代际。默认 IP 策略保留 `v2:策略摘要:IP` 基础键；规则修订、作用域/主体及代际共同约束当前状态，不应把旧格式描述推广到所有策略。站点/保护组处罚按匹配范围投影与执行，旧修订和旧解封代际不能仅因迟到复制而重新生效。独立的全局 IP 封禁不等于这些 scoped CC 决策，作用域解封也不承诺清除无关全局封禁。

共享计数需要一致的规则 ID、执行参数、作用域和来源授权。多节点 route/host 标识与中间件顺序也须一致。CC 解封需要授权签发密钥和持久 generation 栅栏，普通节点的传输密钥不能代签；接收 ACK、当前 boot 的处罚投影确认和实际请求判定是不同证据。见 [CC M4/M5 与后续覆盖机制](cc-m4-m5-focused-verification.md)。

普通 merge 是尽力最终一致路径，没有固定的复制滞后上限。网络分区时按本地状态及覆盖策略处理，恢复后在授权、容量、保留窗口和网络条件允许时尝试收敛。CC 的 `RequireCompleteCoverage` 会在证据不足时抑制相应决策/执行，不能统一描述为所有节点始终独立放行或封禁。短窗口实测包含成功与漏判/降级，不保证任意IO延迟下一秒全局精确判定；见[E3进程验证](cc-e3-process-fault-verification.md)和[当前验收索引](node-communication-final-verification-2026-10-20.md)。

插件幂等占用无法在网络分区下提供严格全局唯一。涉及不可重复外部操作的插件，必须由目标系统提供业务幂等，并采用明确的单写者执行及结果核对协议；当前不新增数据库，也不提供通用的跨系统恰好一次事务。LyWaf 的内置协调器适合抓取、刷新、分析等允许最终一致的后台任务。

## 当前轻量存储选择

| 机制 | 适用场景 | 优点 | 代价与限制 |
| --- | --- | --- | --- |
| 内置 Peer | 中小规模边缘节点 | 无外部依赖，请求热路径可用 | 最终一致，节点数大时全互联成本高 |
| 内置文件权威节点 | 跨节点验证码和一次性工作量证明 | 无新增服务，持久序号、原子消费和重启恢复 | 单权威；失联时验证失败关闭 |
| 持久 Inbox/Outbox | 配置命令、可恢复投递 | 原消息幂等、结果查询、未知状态留证 | 文件容量有界，Unknown 不盲目重放 |

当前保留 `IRuntimeStateStore` 契约，使用本地文件和既有节点通信，不引入新的数据库或消息中间件。共享验证码使用独立的权威节点协议，不经过最终一致复制来消费。配置与验证见[无数据库的跨节点验证码](38-共享验证码存储.md)。

## 插件使用

插件通过 `IPluginContext.Tasks` 使用统一任务协调器：

```csharp
if (!context.Tasks.TryStart("my-plugin", request.IdempotencyKey,
        TimeSpan.FromMinutes(10), out var task))
{
    return task;
}

try
{
    await RunImportAsync(cancellationToken);
    return context.Tasks.Complete("my-plugin", request.IdempotencyKey, true);
}
catch (Exception ex)
{
    context.Tasks.Complete("my-plugin", request.IdempotencyKey, false, ex.Message);
    throw;
}
```

幂等键应由稳定业务标识组成，不能使用每次请求新生成的 GUID，否则无法识别重复任务。

## 两种修复机制与验证边界

### merge 尽力反熵与 v2 批量

反熵补偿已改为有游标的分页遍历：启动即发送一页，此后每30秒推进一页，页大小取QueueCapacity的一半且最多256条；结束后下一轮从头遍历。选页仅保留一页加一条前瞻数据，不再构造完整快照数组。页包含未过期删除墓碑。遍历期间新增且位于游标之前的键会在下一轮纳入。队列拥塞时页内仍可能丢弃，后续轮次继续补偿；尚无逐Peer确认游标，因此这不是无损日志订阅，也不是30秒内必然完成全量修复。

v2普通 merge 发送端将当前Peer队列中已有的变化合为最多32条的数组，不主动等待凑批。预算按完整NodeMessage序列化后的字节数计算，不超过MaxMessageBytes；放不下的下一条留在队列。接收端runtime.merge同时接受旧单条对象和数组，空数组、null项或超过32条均拒绝。批内逐条幂等合并，不保证事务原子性；部分合并后失败的批次可用新 nonce 重签重试，已有计数不会重复累加。成功响应不是 durable spool/接收端 fsync ACK，不能作为长期离线重入或无损交付证明。

### DurableSync 持久 ACK、分页快照与 epoch

两端显式配置 v2、`DurableSyncEnabled`、`runtime.sync` operation 及域/保护组/转发来源权限后才启用；接收方为该 Peer 开启 durable 模式会拒绝普通 merge，不能静默降级绕开。发送端先持久化 pending，按方向流的 epoch/sequence/digest 重试；接收端先持久化日志检查点及收据再返回 Applied。只有匹配 ACK 才推进发送游标。Gap 在保留历史内可重放，历史不足、旧 epoch 或超过离线窗口则进入 SnapshotRequired 流程，不把 HTTP 200 一概当作 ACK。

Bootstrap 需恢复节点显式指定 `BootstrapAuthority`，权威端允许 `AllowBootstrapExport`，且替换范围与授权匹配。已实现 manifest/摘要绑定、分页下载及校验缓存、完整快照安装 fsync、远端新 epoch 提交和发送端重置。替换会移除授权范围内快照不存在的旧键，而非把离线旧视图合回集群；范围外状态保留，CC generation 不倒退。页面下载不等于已安装快照，安装也不等于新 epoch 已获远端确认。

这套分页快照不同于前述每 30 秒一页的本地反熵扫描。DurableSync 保障已准入持久 pending 的交付/恢复，不是每个本地事件的无损日志；其前置队列仍有预算和丢弃边界。快照、历史、缓存和磁盘均有上限，超限安全拒绝，不支持无限大小导出或自动多主权威选举。协议演进见 [P2 durable sync 专项](runtime-state-sync-stage1.md)，其中早期“未实现 bootstrap”段落是历史阶段记录，当前能力以其后续实现、现有代码及下面的进程证据为准。

### 部署后核验

1. 在隔离节点配置唯一 `NodeId`、正确的双方密钥/地址和显式 Send/Receive 权限；v2/durable 模式另核对 operation、bootstrap 权威及替换范围授权，参见 [复制授权专项](runtime-state-replication-authorization.md)。
2. 在节点 A 添加临时封禁，检查节点 B 的状态摘要与实际请求判定。
3. 只停止自建节点 B，在 A 修改状态后重启 B；按所选协议检查反熵进度或 pending/ACK、snapshot/epoch 和最终快照。记录超时与容量/授权拒绝，不把等待 30 秒作为成功判据。
4. 重放完全相同的签名请求，应拒绝 nonce 重放；v1 与 v2 的错误封装不同，v2 使用 `node_replay`，不能依赖统一中文错误文本。
5. 重启自建节点检查未过期状态恢复；DurableSync 另核验检查点、旧 epoch 拒绝和新增量。实际故障点与证据范围分别记录，不以正常重启代替强杀或断电测试。
