# LyWaf 插件整体设计与管理指南

本文依据当前仓库实现整理，覆盖插件架构、开发接入、控制台管理、配置持久化和发布运维。适合插件开发者、控制台开发者和部署维护人员阅读。

本文区分“已经实现”“使用约束”和“后续改进”，不把设计目标当作已经具备的能力。示例 API 使用 `/api/v1`；源码部分路由以 `/api` 注册，由管理端版本处理逻辑适配。

## 1. 设计目标与边界

插件化的目标是让一个功能拥有自己的请求处理、配置、后台任务、管理 API 和页面，同时复用宿主的通用基础设施，而不是把整个宿主复制进插件。

| 责任 | 所属位置 | 原则 |
| --- | --- | --- |
| 监听、反向代理主流程、基础请求上下文 | 宿主 | 提供稳定的执行位置 |
| 插件发现、启停、权限门禁、安装包管理 | 插件宿主 | 不承载具体 CC、图片或认证业务 |
| 控制台身份认证、公共错误契约、准入限制与审计 | 宿主 | 插件不能通过独立业务路由绕过 |
| 功能规则、配置接口、页面内容 | 对应插件 | 不再堆入 ControlApi |
| 共享封禁状态、通用统计持久化等既有服务 | 当前仍在宿主 | 通过服务接口复用，后续再明确拆分边界 |
| 插件私有文件、基线和缓存 | 插件专属数据目录 | 流式访问、限制容量、明确生命周期 |

**当前是同进程模块化架构，不是微服务，也不是不可信代码沙箱。** 外部 DLL 一旦被加载，仍是宿主进程内的 .NET 代码。权限声明可以限制宿主提供的能力，但无法阻止插件直接调用系统文件、网络 API 或使用宿主服务容器。

## 2. 总体结构

```text
管理端浏览器
  +-- 插件管理：列表 / 启停 / 配置 / 安装 / 回滚
  +-- 动态插件菜单 -> 插件 Vue 页面 -> 插件前端 api.ts
                                      |
                         /api/v1/plugins/{id}/proxy/{path}
                                      |
宿主管理入口：身份与权限 -> 准入限制 -> 插件状态与 ConsoleApi 授权
                                      |
                           IPluginApiHandler
                                      |
                     插件业务服务 / 共享宿主服务

代理流量 -> 宿主固定管道 -> 插件高优先级入口
                         -> 请求防护阶段
                         -> 响应监控阶段
                         -> 插件普通优先级入口 -> 上游

PluginManager -> 发现 / 服务注册 / 初始化 / 启动 / 停止
插件上下文    -> 配置快照 / 日志 / 文件流 / 网络客户端 / 事件 / 任务
```

这只是插件相关的结构图，不表示省略了 WAF、验证码、限流等核心中间件。实际顺序以 `Program.cs` 为准。

## 3. 插件类型与发现

插件可以来自已经加载的程序集，也可以来自外部插件目录。内置实现通常放在 `Plugins/Sys/`；示例放在 `Plugins/Examples/`。

外部加载目前支持两种布局：

```text
plugins/
  Example.Plugin.dll                 # 旧式根目录 DLL 布局
  example-plugin/
    current.json                     # 包管理器维护的当前版本指针
    versions/
      1.0.0/Example.Plugin.dll
      1.1.0/Example.Plugin.dll
```

包管理布局只加载当前指针指定的入口，不应扫描历史版本当作多个插件。不要手工混放相同 ID 的不同版本。

“内置插件”和“系统插件”不是完全相同的概念：前者描述程序集来源，后者描述宿主信任分类。当前管理器的系统插件集合包含 `request-logger`、`analysis`、`web-tamper`。系统插件获得宿主信任，不走外部插件包替换流程。

`PluginMetadata.Id` 同时参与配置、目录、菜单和 API 路径，应使用稳定、唯一的标识。更改 ID 不等于普通版本升级，需要处理原有配置和数据归属。

## 4. 生命周期与启停

典型流程为：

```text
发现插件 -> ConfigureServices -> InitializeAsync -> StartAsync
                                                    |
                                                Running
                                                    |
                                               StopAsync
                                                    |
                                                Stopped
```

状态枚举还包括 `Unloaded`、`Loaded`、`Initialized`、`Error`。它们描述运行过程，不能替代持久化的启用意图。

| 方法 | 应做的工作 | 不应做的工作 |
| --- | --- | --- |
| `ConfigureServices` | 注册依赖与配置绑定 | 启动线程、拉取远端、写业务数据 |
| `InitializeAsync` | 读取配置、初始化资源、准备订阅 | 留下无法清理的重复订阅 |
| `StartAsync` | 启动可取消的后台工作 | 忽略重复启动和取消信号 |
| `StopAsync` | 取消任务、释放订阅、关闭句柄 | 删除业务配置或自动解除所有封禁 |
| `ConfigureProxyPipeline` | 装配请求处理链 | 根据启动时 Enabled 值永久省略处理链 |

当前所有已发现插件都会注册服务，以支持启动时禁用、运行后再启用。因此，**禁用不是“不加载代码”或“不注册服务”**。

代理管道通过 `UseWhenActive` 在每次请求进入时检查 `Running`。禁用后新请求跳过插件；已经进入插件的请求允许完成。重新启用已发现插件不需要重新装配管道。

菜单和插件 API 当前允许 `Running`、`Initialized`；代理请求处理要求 `Running`。初始化期间看到菜单，不代表后台任务已经开始运行。

启停及配置重载通过激活锁和配置修订号协调，避免旧配置回调覆盖新状态。但生命周期超时不等于强制终止线程；插件仍必须正确处理取消和资源释放。

## 5. 请求管道扩展

### 5.1 通用代理入口

重写 `ConfigureProxyPipeline` 注册插件中间件。`Highest`、`High` 放在高优先级入口，`Normal`、`Low`、`Lowest` 放在普通入口。优先级只决定对应入口内的插件顺序，不能任意越过主程序的固定阶段。

动态业务配置应在请求执行时读取，不要只在管道装配时读取一次。中间件如处理请求体，必须保留后续消费者需要的读取能力，并限制缓冲大小。

### 5.2 固定业务阶段

当前新增 `IPluginProxyStages`，用于需要精确位置的内置插件：

| 阶段 | 当前位置 | 流量分析插件用途 |
| --- | --- | --- |
| `RequestProtection` | 验证码之后、限流之前 | CC 规则检查和处置 |
| `ResponseMonitoring` | 限流之后 | 下游错误响应统计 |

主程序只调用阶段入口，流量分析插件决定注册 `CcProtectionMiddleware`、`CcResponseMonitorMiddleware`。

**SDK 边界：** `PluginProxyStage.cs` 当前未被独立 SDK 工程编入，因此 `IPluginProxyStages` 是宿主内部扩展，不应在只引用 `LyWaf.PluginSdk` 的外部插件示例中直接使用。外部插件目前使用 SDK 中的通用管道接口。

`ConfigureMiddleware` 是另一种宿主中间件扩展入口，不应假设它与代理管道具有完全相同的动态启停行为；需要热切换的代理功能优先使用已加门禁的代理入口。

## 6. 配置与启用状态持久化

### 6.1 基础配置示例

以下片段使用 `config.ly` 的 Plugins 解析方式：

```ly
Plugins {
    Enabled = true
    PluginDirectory = "plugins"
    DataDirectory = "plugin_data"
    LifecycleTimeoutSeconds = 30

    Permissions {
        example-plugin = "ConsoleApi, DataDirectory"
    }

    PluginConfigs {
        example-plugin {
            Enabled = true
            MaxItems = 1000
        }
    }
}
```

示例只说明配置结构，不代表 `example-plugin` 已经安装。插件自定义配置会映射到 `Plugins:{pluginId}`，由插件自身解释；`MaxItems` 不是宿主通用配置项。

### 6.2 启用意图优先级

从高到低：

1. `Plugins:EnabledOverrides:{id}`。
2. `PluginConfigs` 中该插件的 `Enable`/`Enabled` 等启用字段。
3. `DisabledPlugins` 列表。
4. 系统插件默认值或元数据中的 `EnabledByDefault`。

管理端切换会把结果写入配置补丁的 `PluginEnabledStates`，由配置加载器映射到 `EnabledOverrides`。因此，后台已经保存的状态可能覆盖你在基础配置里修改的 Enabled 值。

上面的优先级只决定启用意图。外部插件仍需满足权限要求，并成功初始化、启动，才能真正运行。

### 6.3 配置快照与热更新

`IPluginContext.Configuration` 是构造上下文时生成的插件配置快照，`GetPluginConfig<T>()` 基于该快照绑定。它不是一个自动更新的全局配置视图。

需要热更新时，插件服务应在 `ConfigureServices` 中明确注册自己的 `IOptionsMonitor<T>` 绑定，并在使用时读取最新值。仅仅把属性类型改成 `IOptionsMonitor<T>`，不会自动建立配置绑定。

通用配置编辑依赖元数据的 `DefaultOptions`，适合简单选项。条件组、资源基线等复杂模型应提供插件专用 DTO、校验和页面，不应塞进通用字符串配置字典。

敏感字段不要通过默认选项和配置查询原样回传。配置检查接口应返回“是否已设置”等状态，而不是密码、令牌或私钥。

## 7. 控制台菜单、页面与 API

### 7.1 三个独立环节

1. 后端 `GetActions()` 声明菜单。
2. 前端 `plugin.ts` 注册可渲染的 Vue 路由。
3. 后端 `IPluginApiHandler` 提供页面调用的业务接口。

注册菜单不会自动生成页面；安装包包含前端文件也不等于当前 Vue 应用已经动态加载这些文件。

菜单示例：

```csharp
public override IReadOnlyList<PluginAction> GetActions() =>
[
    new PluginAction
    {
        Id = "manage",
        Name = "示例管理",
        Type = "page-link",
        Path = "/plugins/example-plugin/manage"
    }
];
```

菜单目录限制路径在 `/plugins/{id}` 内，拒绝外部地址、父目录跳转及不允许的编码路径。控制台通过 `/api/v1/plugins/menus` 获取菜单；启停后立即刷新，另有周期刷新同步其他会话的变化。

前端模块示例：

```ts
// Frontend/src/plugins/example-plugin/plugin.ts
import type { RouteRecordRaw } from 'vue-router'

export default {
  path: '/plugins/example-plugin/manage',
  name: 'ExamplePluginManage',
  component: () => import('./Manage.vue'),
  meta: { title: '示例管理', pluginId: 'example-plugin' },
} satisfies RouteRecordRaw
```

模块扫描发生在前端构建阶段。新增 `Manage.vue` 和路由后必须重新构建控制台。

### 7.2 业务接口统一代理

```text
/api/v1/plugins/example-plugin/proxy/status
                        -> HandleApiAsync("status", context)
```

推荐把分派入口、请求模型和业务实现放在插件目录，不再向 `ControlApi` 添加具体功能接口：

```text
Plugins/Sys/Example/
  ExamplePlugin.cs
  ExampleAdminApi.cs
  ExampleApiModels.cs
  ExampleService.cs
Frontend/src/plugins/example-plugin/
  plugin.ts
  Manage.vue
  api.ts
```

前端调用：

```ts
import { pluginProxyApi } from '@/api'

const proxy = pluginProxyApi('example-plugin')
export const exampleApi = {
  status: () => proxy.get<{ success: boolean }>('status'),
}
```

插件处理器应按 HTTP 方法和相对路径分派，未知路由返回 404。插件内部手工读取 JSON 时，需要自行调用校验逻辑；代理入口无法自动知道插件读取了哪个 DTO。

CC 目前通过 `ManagementBodyValidation.ValidateBody` 复用有界递归校验，并通过宿主错误过滤器保持统一响应。这个校验器属于宿主实现，不属于外部 SDK；外部插件应实现等效输入校验，不能反向引用宿主内部工具来假装获得稳定契约。

### 7.3 宿主保留的管理端点

以下路径相对于 `/api/v1/plugins`：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | 空路径 | 分页插件列表与实际状态 |
| GET | `/menus` | 可显示的插件菜单 |
| POST | `/toggle` | 切换插件状态并保存 |
| GET / POST | `/{pluginId}/config` | 查询、修改通用配置 |
| GET | `/{pluginId}/actions` | 查询动作 |
| POST | `/{pluginId}/actions/{actionId}` | 执行动作 |
| POST | `/install` | 上传安装包 |
| POST | `/{pluginId}/rollback` | 切换包版本指针 |
| GET / POST / PUT / PATCH / DELETE | `/{pluginId}/proxy/{path}` | 转发插件业务 API |

`toggle` 当前是切换操作，不是“设置成指定状态”的幂等语义。控制台应等待响应后更新状态，不应把重复点击或网络重试当成无副作用操作。

## 8. 权限、安全和容量

访问插件页面与 API 涉及不同层面的检查：管理端身份和读写权限、插件运行状态、插件的 `ConsoleApi` 能力授权。隐藏菜单不是后端访问控制。

| 能力 | 作用 |
| --- | --- |
| `Network` | 使用宿主提供的网络客户端工厂 |
| `DataDirectory` | 使用宿主提供的插件文件流存储 |
| `ConsoleApi` | 通过统一代理处理控制台请求 |
| `SensitiveConfiguration` | 读取插件配置快照中被判定为敏感的字段 |

当前配置快照按字段名中的 password、secret、token、key 等片段过滤敏感项。这是启发式过滤，不应将其视为完备的数据分类或隔离机制。

`PluginApiProxyOptions` 的默认值：请求体上限 1 MiB、每用户与插件组合每分钟 120 次、全局并发 16。准入器按 Content-Length 做大小预检；没有长度的流式请求还需要依赖宿主管理请求体限制，不能把预检当作逐字节计量。

典型结果：未启用插件返回 503，缺少 ConsoleApi 返回 403，未知插件或业务路径返回 404，超过准入限制返回 413 或 429。业务校验失败通常为 400。客户端应保留错误状态和错误详情，不能将失败响应包装成成功。

对文件与远端访问还应遵守：

- 使用 `IPluginStorage.OpenRead/OpenWrite` 和有限缓冲，不整文件载入内存。
- 网络操作设置超时、取消、最大响应体和最大并发。
- 日志、队列、缓存和去重键必须有容量上限及淘汰规则。
- 写入采用临时文件与原子替换，失败时关闭句柄并清理临时资源。
- 不可信插件需要进程、容器和操作系统权限隔离；当前宿主不提供这种隔离。

## 9. 后台任务与事件

插件可通过 `PublishEventAsync`、`SubscribeEvent` 进行进程内通信。订阅返回的 `IDisposable` 应由插件保存并在停止时释放，重新启用时避免重复订阅。

`IPluginTaskCoordinator` 提供按插件 ID 和幂等键协调任务的能力，返回 `PluginTaskState`，包括状态、开始/结束时间及错误信息。它不等于持久化消息队列或跨节点一致性调度器，业务不能据此假设重启后任务自动恢复。

推荐后台工作流程：启动时建立取消源和有界队列，处理时检查取消，结束时更新任务状态，停止时取消并等待退出。连接失败、远端超时属于可预期结果，应转换为业务状态或受控重试，而不是无限重试或吞掉所有异常。

## 10. 当前流量分析插件的完整链路

流量分析插件 ID 为 `analysis`，页面为 `/plugins/analysis/cc`。

```text
CC 页面 -> Frontend/src/plugins/analysis/api.ts
        -> /api/v1/plugins/analysis/proxy/...
        -> AnalysisPlugin.HandleApiAsync
        -> AnalysisAdminApi
        -> IStatisticService / 宿主审计与共享状态

代理请求 -> 插件阶段 -> CC 规则检查 -> 封禁协调器 -> 共享封禁状态
后台流量分析 ---------------------------+
                                      +-> 最近 1000 条 CC 封禁日志
```

已迁移的管理接口包括基础规则、高级条件组规则、白名单路径、路径统计配置。旧 `/api/cc/*` 和 `/api/statistic/*` 管理路由已移除；具体接口表见 [插件代理管道阶段](plugin-proxy-stages.md)。

禁用 analysis 后，新请求不再进入该插件的 CC 检测与统计管道，业务代理不能继续访问。已有封禁不自动清除。封禁协调器避免同一进程内重复封禁仍在有效期的 IP，日志最多保留 1000 条，重启后日志清空。

尚未完全独立的部分：`IStatisticService` 及实现、CC 检测相关类型、共享封禁等仍位于宿主。当前迁移完成的是接口与装配归属，不是 analysis 已可作为不依赖宿主的独立 SDK 包发布。

## 11. 新建插件的实施顺序

1. 明确功能边界：规则是什么、哪些数据私有、哪些服务需要共享。
2. 选择内置模块或外部 SDK 插件。外部插件从 `sdk/templates/LyWaf.Plugin.Template` 起步。
3. 定义唯一 ID、版本、默认状态及最小权限，避免依赖宿主内部具体类型。
4. 注册依赖，实现可重复启停的生命周期和资源清理。
5. 添加请求管道或后台任务，设置内存、并发、队列和超时上限。
6. 在插件目录实现业务 API、DTO 和校验，入口接入 `IPluginApiHandler`。
7. 添加页面路由、菜单动作和插件 `api.ts`，验证禁用后的访问行为。
8. 测试配置保存、重启恢复、启停竞争、权限不足和异常场景。
9. 需要外部分发时再进行包清单、哈希、签名及数据版本迁移设计。

独立 SDK 当前版本为 1.0.0，工程只编入部分公开契约源文件。版本和 API 可用性以 SDK 工程实际产物为准，不是 `Plugins/Core` 下的所有类都能被外部插件引用。

## 12. 安装、升级、回滚与日常管理

### 12.1 包发布

`.lyplugin` 是 ZIP 包，根目录包含 `plugin.json`。清单描述入口程序集、插件版本、SDK/数据/前端版本和文件 SHA-256。宿主限制压缩大小、解压总量、文件数量，并校验路径、哈希及按配置要求的签名。

默认上限分别为 100 MiB、250 MiB、512 个文件。签名强制校验默认未启用；生产部署应配置可信签名键并启用签名要求。不要把默认配置误解为“任何包都已经验证发布者身份”。

包中不应携带宿主提供的 `LyWaf.PluginSdk.dll`，避免契约程序集身份不一致。完整清单和签名说明见 [安装升级与回滚](56-插件安装升级与回滚.md)。

### 12.2 重启边界

| 操作 | 当前处理方式 |
| --- | --- |
| 启停启动时已发现的插件 | 运行时切换代理执行门禁 |
| 修改业务配置 | 取决于插件是否正确订阅热更新，不能一概而论 |
| 安装或升级包 | 写入版本目录和 current.json，返回需要重启 |
| 包回滚 | 切换版本指针，仍需重启 |
| 新增 Vue 插件模块 | 重新构建控制台 |
| 增加新插件服务类型 | 不能向已经构建的容器直接补注册，需重启 |

虽然存在 `EnableHotReload` 配置和 `ReloadPluginAsync` 方法，当前不能据此承诺 DLL、DI 容器、已捕获的请求管道与前端模块可以完整无重启升级。生产环境按照“包更新后重启”操作。

### 12.3 数据迁移与回滚

数据版本变更通过 `IPluginDataMigrationProvider` 提供迁移链，在初始化前执行。代码回滚不代表数据自动回滚；降级需要反向迁移或经过验证的备份恢复方案。

升级前记录版本、启用状态和授权，备份私有数据及共享服务中属于该功能的持久化状态。升级后核对实际运行版本、菜单、业务请求和后台任务。禁用、停止、回滚都不等于卸载和删除数据。

## 13. 验证与排障清单

| 现象 | 优先检查 |
| --- | --- |
| 重启后启用状态与预期不一致 | EnabledOverrides、补丁 PluginEnabledStates、基础配置和权限 |
| 提示启用成功但不处理请求 | 实际 State 是否 Running、是否注册到正确代理入口 |
| 禁用后仍有影响 | 已进入的请求、已有封禁、未停止的后台任务、宿主独立逻辑 |
| 菜单不存在 | GetActions、运行状态、路径合法性、菜单刷新 |
| 菜单存在但页面无法打开 | plugin.ts 是否被扫描、Vue 组件是否已构建 |
| 插件 API 为 503 / 403 | 分别检查插件状态 / 管理权限和 ConsoleApi 授权 |
| API 输入非法却成功 | 是否在插件内部读取 JSON 后执行完整校验 |
| 配置修改不生效 | 上下文快照、IOptionsMonitor 绑定、覆盖优先级 |
| 包升级后还是旧版本 | current.json、重启情况、元数据与清单一致性 |
| 重启后日志消失 | 日志是否明确设计为内存环形缓存 |

交付前至少覆盖：启停与重启恢复、无权限与禁用请求、CRUD 与分页、错误条件组、请求体边界、超时与取消、队列满、文件越界、数据迁移失败以及回滚。

仓库已有相关测试：`AnalysisPluginApiTests`、`PluginProxyStageTests`、`PluginActivationPersistenceTests`、`PluginActivationConcurrencyTests`、`PluginMenuTests`、`PluginApiAdmissionGateTests`、`PluginDataMigrationTests`。前端 `api-contract.test.mjs` 验证 CC 调用统一代理。

```powershell
dotnet test tests/LyWaf.Tests -c Release --no-restore
```

测试结果属于具体代码版本；不要把文档中列出的测试类当作当前部署环境已经通过验收的证明。

## 14. 后续改进方向

以下是建议，不是现有承诺：

- 将适合外部插件使用的固定阶段契约纳入 SDK，并定义兼容规则。
- 继续梳理 CC 检测、统计配置持久化与共享封禁的接口边界。
- 完善插件私有业务路由的机器可读 API 契约和权限描述。
- 将状态切换改进为明确设置目标状态，减少重复请求导致的反向切换。
- 完善插件依赖关系校验和启动顺序，不把 Dependencies 字段本身当作完整依赖调度器。
- 对需要隔离的不可信扩展，引入独立进程与资源限制，而不是扩大同进程权限。
