# 多进程 Worker 模型评估

## 结论

LyWaf 当前保持单宿主、多线程异步 I/O 模型，不在单机上自动派生多个 Worker 进程。生产扩容使用多个独立 LyWaf 实例，由四层负载均衡器、容器编排平台或 systemd 模板实例分配不同地址或端口。

这不是永久否定多进程，而是避免在状态共享和数据写入尚未外置时提供一个表面可用、实际语义错误的开关。

## 当前单宿主能力

- Kestrel、YARP、TCP/UDP Stream 均使用异步网络 I/O，一个进程可以使用多个线程和全部可用 CPU。
- 请求处理没有 Nginx 单 Worker 的单线程事件循环限制，因此“每 CPU 一个进程”不是默认前提。
- 后台任务、插件生命周期、证书管理和优雅停止目前都以一个 .NET Generic Host 为所有权边界。
- `MaxConnections`、请求限速和 Stream 会话上限均在单实例内严格生效。

是否满足目标负载必须通过 `docs/29-性能基准.md` 的方法测量 CPU、吞吐、P99 延迟、GC 暂停和内存，而不能仅依据进程数判断。

## 直接启动多个 Worker 的问题

| 领域 | 当前状态 | 多 Worker 风险 |
|---|---|---|
| 监听端口 | Kestrel/TCP/UDP 由单宿主绑定 | 跨平台端口复用语义不同，UDP 会话也可能漂移 |
| WAF 与 CC 状态 | `SharedData` 和多个并发字典在进程内 | 每个进程独立计数，攻击者可按 Worker 放大额度 |
| 验证码与认证临时态 | 进程内缓存 | 后续请求落到其他 Worker 时无法验证 |
| 响应缓存和插件状态 | 本地内存或本地目录 | 重复占用空间，失效和版本无法原子同步 |
| 统计持久化 | 单个 DuckDB 文件与后台批量刷写 | 多写进程会产生锁竞争，不能作为共享协调数据库 |
| 配置、证书和升级 | 单宿主生命周期 | 需要跨进程版本栅栏、签发锁和统一排空 |
| 指标 | 进程内累计值 | 必须保留实例标签并由监控端聚合 |

因此，同机多进程不能共享同一 DuckDB 文件和可写数据目录，也不能把进程内限流解释为节点级限流。

## 当前推荐部署

1. 每个实例使用独立的数据目录、DuckDB 文件、控制端口和必要的 Stream 监听端口。
2. HTTP 实例置于支持健康检查和连接排空的外部负载均衡器后。
3. 需要跨实例一致性的 CC 限流、验证码、会话和配置状态应先外置到明确的共享存储。
4. 停止实例时使用 LyWaf 的平滑停止流程，让在途 HTTP、TCP 和后台刷写完成。
5. Prometheus 按实例采集后聚合，不在实例内合并多进程计数。

## 重新评估的触发条件

只有同时满足以下条件，才实施宿主内 Worker 管理器：

- 基准证明单进程在 CPU 已饱和时吞吐无法随线程继续增长，并排除锁竞争、分配和配置问题。
- 限流、验证码、缓存失效、插件状态和证书签发拥有跨进程一致性方案。
- DuckDB 改为每 Worker 独立文件后汇总，或替换为支持目标并发写入的外部存储。
- Windows 与 Linux 均验证 HTTP、TCP、UDP 端口复用；不支持的平台使用父进程分发已接受的连接或独立端口。
- Worker 崩溃拉起、滚动升级、连接排空、日志归属和指标实例标签已有集成测试。

## 决策

现阶段不新增 `Workers` 配置项。若用户需要纵向利用多核，先测量单宿主；需要更高容量或故障隔离时，运行多实例并使用外部负载均衡。该方案保持状态边界清晰，也与后续多节点配置分发能力一致。
